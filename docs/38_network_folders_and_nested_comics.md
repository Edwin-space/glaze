# 네트워크는 폴더로, 만화는 압축 안의 압축까지 (2026-09-08)

## 1. 네트워크 — 트리를 훑던 것을 폴더 탐색으로

### 무엇이 문제였나

서버에 붙으면 **고른 폴더 아래 전부를 훑었다.** 폴더를 세어가며 내려가고, 그 결과로
포스터 격자를 만들고, **접속할 때마다 처음부터 다시 했다.** 고를 수 있는 것도 1차
폴더뿐이어서 그 아래에 무엇이 얼마나 있든 통째로 딸려왔다.

영화 몇천 편이 있는 NAS에서는 화면에 무엇이 나타나기까지 요청이 수천 번 오간다.
그리고 그렇게 만든 것을 앱을 닫으면 버렸다. 게다가 NAS의 대부분에는 포스터가 없으니,
그 값을 치르고 얻은 것은 회색 사각형의 격자였다.

### 정한 것

**보고 있는 폴더만 묻는다.** 폴더를 여는 데 드는 요청은 아래에 무엇이 있든 **한 번**이고,
아무도 열어보지 않은 폴더는 읽지 않는다.

- `IOSNetworkBrowser` — 시놀로지와 WebDAV를 같은 모양으로 한 폴더씩 읽는다
- 폴더 하나 = 요청 하나. 자막과 포스터는 **같은 목록에서** 찾으므로 추가 요청이 없다
- 영상 옆 `.nfo`는 **일부러 읽지 않는다.** 폴더의 영화 수만큼 요청이 늘어나는데,
  그게 바로 이 개편이 없애려는 비용이다. 이름을 해석해서 쓰고, `.nfo`는 사람이
  실제로 물어본 한 편에 대해서만 읽는다
- 이미 읽은 폴더로 돌아와도 서버에 다시 가지 않는다. 예전 라이브러리는 화면이 나타날
  때마다 전부 다시 읽었고, 그것이 앱이 늘 생각에 잠긴 것처럼 보이던 이유다

### 보기 방식 — 아이콘 · 목록 · 갤러리

파일 앱이 주는 세 가지를 그대로. 각각 다른 질문에 답하기 때문이다 — *여기 뭐가 있지*
(아이콘), *어느 것이지* (목록, 크기와 자막 수가 들어간다), *저게 무슨 영화지*
(갤러리, 그림이 알아볼 만큼 크다).

포스터는 **갤러리에서만** 가져온다. 아이콘 크기에서는 알아볼 수 없고, 타일마다
요청이 하나씩 붙기 때문이다.

## 2. 만화가 서재에 없었다 — 압축 안의 압축

### 무엇이 있었나

실기기의 `만화` 폴더를 그대로 열어봤다:

```
ba-na-na.zip                      109개 항목, 이미지 109
경사청 24시.zip                     7개 항목, 이미지   1   ← [Cover].jpg + zip 6개
대물(완).zip                       74개 항목, 이미지   0   ← 전부 zip
란제리.zip                          1개 항목, 이미지   0   ← zip 하나
엿보기구멍.zip                     12개 항목, 이미지   0
오! 나의 여신님.zip              4868개 항목, 이미지 4818
출동! 119구조대(완).zip            20개 항목, 이미지   0
...
```

**열일곱 중 열여섯이 이미지가 아니라 또 다른 zip을 담고 있었다.** 권마다 zip으로 묶고
그것들을 다시 하나로 묶은 형태 — 한국에서 만화가 가장 흔하게 유통되는 모양이다.

서재는 "이 압축 안에 이미지가 있나?"를 묻는다. 답이 아니오였고, **책은 한마디 말도 없이
버려졌다.** 표지가 든 것들은 더 나빴다: `[Cover].jpg` 한 장을 통째로 책이라고 여겨서
20권짜리 전집이 **한 장짜리 책**이 됐다.

### 고친 것

- 안쪽 아카이브를 **권으로 취급한다.** 기존의 "한 아카이브 = 한 시리즈" 구조에 그대로
  얹힌다 — 폴더로 나뉜 것과 zip으로 나뉜 것이 같은 것이므로
- 안쪽 zip은 deflate로 눌려 있어 있는 자리에서 읽을 수 없다(zip은 목차를 seek해야 한다).
  캐시 폴더에 한 번 풀어두고 보통 아카이브로 읽는다 — `.7z`가 이미 하고 있는 거래다
- **안쪽 아카이브가 표지 이미지를 이긴다.** 표지 한 장이 스무 권을 가리지 않도록
- 아카이브를 여는 것은 **바깥쪽 목차만** 본다. 권마다 열어서 판단하면 라이브러리 전체를
  훑는 비용이 스캔으로 돌아오고, 그게 방금 없앤 것이다

### 확인한 것 — 실기기의 진짜 파일로

기기에서 그 폴더를 그대로 가져와 로더를 직접 돌렸다.

| | 이전 | 지금 |
|---|---|---|
| 단행본 | 8 (그중 4개는 표지 한 장짜리 가짜) | 4 |
| 전집 | 0 | **12** |

```
경사청 24시 — 6권      교과서엔 없어! — 19권    대물 — 74권
러브 인 러브 — 14권     미스터리 극장 에지 — 25권  번역판 — 6권
선생님과 열애중 — 8권   슬램덩크 완전판 — 24권    엿보기구멍 — 12권
오! 나의 여신님 — 46권  우리 옆집 사모님 — 21권   출동! 119구조대 — 20권
```

그리고 **페이지가 실제로 읽힌다** — 안쪽 zip을 풀어 1권 1쪽을 열어 크기까지 확인:

```
경사청 24시   1권: 98쪽, 첫 쪽 204,874바이트, 1158×784
교과서엔 없어! 1권: 108쪽, 582×768
대물          1권: 87쪽, 902×651
러브 인 러브   1권: 97쪽, 1600×1200
```

회귀 테스트 두 개(`NestedComicArchiveTests`)로 묶었다 — zip 안의 zip이 권으로 잡히는지,
표지가 권들을 가리지 않는지. 테스트 310개 통과.

## 확인하지 않은 것

- **실기기 서재 화면.** 로더가 옳게 읽는 것은 확인했지만, 아이폰 화면에서 12개 전집이
  어떻게 보이는지는 직접 보지 못했다
- **네트워크 폴더 탐색을 실제 NAS에서.** 시놀로지 주소 문제(`docs/34`)를 아직 실기기에서
  통과하지 못해 서버 안쪽을 열어보지 못했다
- 첫 권을 풀어 표지를 만드는 비용. 전집 12개면 캐시가 수백 MB까지 갈 수 있다 —
  캐시를 비우는 자리가 아직 없다

## 3. 큰 만화가 느렸던 이유 — 표지 한 장에 권 하나를 통째로 (같은 날, 고침)

큰 zip 만화를 열면 오래 걸린다는 보고. 다른 만화 앱과 속도 차이가 크다고.

### 짐작하지 않고 쟀다

먼저 zip 읽기 자체를 의심했는데, 아니었다. 288MB · 240쪽 아카이브로:

```
holdsPages            1 ms
ComicArchive.open     7 ms      (목차 읽기)
imageData(at: 0)      1 ms
imageData(마지막)      1 ms
```

**zip 계층은 빠르다.** 병목은 그 위였다.

### 진짜 원인 — 오늘 내가 넣은 것

전집 화면은 **권마다 표지를 그린다.** 그런데 중첩 압축을 지원하면서, 표지 한 장을
얻으려고 **안쪽 zip을 통째로 풀어 캐시에 쓰고** 있었다. `대물`은 74권이다. 표지가
하나라도 보이기 전에 **1GB가 넘게** 풀려 디스크에 쓰인다.

`.7z` 경로에는 이미 같은 이유의 방어가 있었다 — *"선반 가득한 7z의 썸네일을 그리려고
전부 풀 수는 없다"*. 중첩 zip에도 같은 논리가 필요했고, 다만 zip은 **싸게 할 수 있다.**

### 고친 것 — 앞에서만 읽는다

zip의 목차는 파일 끝에 있지만, **첫 멤버의 로컬 헤더는 맨 앞에 있다.** 표지에 필요한
것은 그 앞부분뿐이다.

- `ZipArchive.firstMember(inPrefix:where:)` — 중앙 디렉터리 없이, 앞에서부터 로컬
  헤더를 짚어 첫 페이지를 꺼낸다
- 안쪽 아카이브는 **앞 6MB만** 풀어본다. 디스크에는 아무것도 쓰지 않는다
- 이미 풀려 있으면(누군가 그 권을 읽었으면) 그것을 쓴다
- 권을 **실제로 읽을 때는** 여전히 통째로 푼다. 페이지를 넘기려면 그 방법뿐이므로

12권짜리 226MB 전집으로 잰 값:

| | 시간 | 디스크에 쓴 양 | 표지 |
|---|---|---|---|
| 앞부분만 읽기 | **51 ms** | **0 MB** | 12/12 |
| 권마다 풀기(이전) | 220 ms | 226.8 MB | 12/12 |

74권짜리에서는 이 차이가 1GB 대 0이 된다.

### 테스트가 잡아낸 덤

회귀 테스트를 붙이자 **캐시 키 결함**이 드러났다. 캐시가 아카이브의 *이름*과 크기로
키를 만들고 있어서, 같은 이름·같은 크기의 서로 다른 다운로드가 **서로의 페이지를
보여줄** 수 있었다. 경로로 바꿨다.

테스트 311개 통과.

## 아직 확인하지 않은 것

- 실기기에서의 체감. 맥에서 잰 값이고, 아이폰은 I/O가 느려 절대값은 다르다 —
  다만 **쓰지 않는 1GB**는 어느 기기에서든 쓰지 않는다
- 캐시를 비우는 자리는 여전히 없다. 권을 읽으면 그만큼 쌓인다
