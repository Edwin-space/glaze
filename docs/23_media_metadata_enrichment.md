# 작품 정보 가져오기 — 조사 결과

작성일: 2026-08-26

"IMDb에서 포스터와 공식 제목을 받아 영상 파일 속성에 써 두면 Apple TV가 DLNA로 같이 불러올 수 있지 않나"는 제안에 대한 확인이다. 세 갈래로 나눠 확인했고, 두 개는 결론이 났고 하나는 NAS가 꺼져 있어 남았다.

## 1. IMDb API는 쓸 수 없다

공개 API가 없다. IMDb 데이터는 AWS Data Exchange를 통한 기업 계약으로만 제공되고 진입 가격이 연 15만 달러 수준이다.

**실질적인 후보는 TMDB다.** 무료이고 한국어 제목·줄거리·포스터를 제공한다. 다만 약관에 주의할 점이 있다. 공식 API 약관은 "상업적 이용은 별도 계약 없이 허용되지 않는다"고 하면서, 같은 곳의 안내는 "광고가 붙거나 유료로 판매하는 소프트웨어는 괜찮고 출처만 표기하면 된다"고 한다. **유료 앱으로 출시할 것이므로 이 부분은 확인이 필요하다.** 대안으로 OMDb(무료 티어 1일 1,000회)가 있다.

## 2. 파일에 쓰는 것은 된다. 빠르고, 위험하다

번들된 ffmpeg로 확인했다.

- **MKV**: `-attach cover.jpg` + `-metadata:s:t:N mimetype/filename`. 첨부 이름을 `cover.jpg`로 두는 것이 Matroska의 커버 아트 관례이고 Kodi·Plex·Synology가 모두 이 이름을 본다.
- **MP4**: 커버를 두 번째 입력으로 넣고 `-disposition:v:1 attached_pic`.
- **비용**: 1.7GB MKV에 커버와 태그를 넣는 데 **2.1초**(스트림 복사, 디스크 속도가 한계). 재인코딩은 없다.

**그러나 컨테이너를 통째로 다시 쓴다.** 두 가지가 따라온다.

1. 원본 크기만큼 여유 공간이 필요하고, SMB로 마운트한 NAS라면 1.7GB를 읽어 1.7GB를 쓰는 왕복이 된다. 로컬의 2.1초와는 다른 이야기다.
2. **원본에 있던 것이 망가질 수 있다.** 실제로 당했다. `-metadata:s:t`는 **모든 첨부 스트림**에 적용되므로, 기준 파일의 TTF 폰트 3개가 전부 `cover.jpg`로 덮어써져 ASS 자막이 글꼴을 잃었다. 기존 첨부 개수를 세어 `-metadata:s:t:N`으로 새 첨부만 지목해야 한다.

사용자의 영상 파일을 고치는 기능이므로, 원본을 제자리에서 덮어쓰기 전에 검증하는 절차가 반드시 필요하다.

## 3. DLNA가 그것을 다시 내보내는가 — 미확인

**이 질문이 제안 전체를 결정한다.** 파일에 아무리 잘 써도 DLNA 서버가 `upnp:albumArtURI`로 노출하지 않으면 Apple TV는 볼 수 없다.

NAS가 절전에 들어가 확인하지 못했다. 확인 방법:

1. 커버를 넣은 파일을 NAS에 두고 미디어 서버를 다시 색인시킨다.
2. ContentDirectory `Browse`의 DIDL 응답에 `<upnp:albumArtURI>`가 생기는지 본다.

앞선 조사에서 Plex와 Synology 응답 어디에도 `albumArtURI`가 없었지만, 그때 표본은 커버가 없는 파일들이었으므로 결론이 되지 못한다.

## 더 짧은 길이 있다

Apple TV 앱은 네트워크를 쓸 수 있다. 이미 만들어 둔 `MediaTitleParser`가 제목과 연도를 뽑으므로, **TV가 TMDB를 직접 호출**하면 된다. Plex와 Infuse가 실제로 하는 방식이다.

| | 파일에 써 두기 | TV가 직접 조회 |
|---|---|---|
| 파일 수정 | 필요 | 없음 |
| Mac이 만진 적 없는 영상 | 안 됨 | 됨 |
| 오프라인 | 됨 | 안 됨 |
| DLNA 재노출 의존 | **있음(미확인)** | 없음 |
| NAS가 진실의 출처 | 부합 | 부합하지 않음 |

둘은 배타적이지 않다. Mac에서 작품 정보를 맞추고 파일에 써 두는 것은 그 자체로 값이 있고(Mac 라이브러리도 포스터와 제대로 된 제목을 얻는다), Apple TV는 확실한 경로인 직접 조회를 쓰되 DLNA가 커버를 내보내는 것이 확인되면 그쪽을 우선하면 된다.
