# 아이폰·아이패드 정식 출시 준비 — 지금 상태와 남은 일

작성일: 2026-10-06 · 대상: iOS/iPadOS

## 1. 이번에 넣은 것 — 최초 실행 안내

없던 것이다. 앱을 처음 열면 빈 폴더와 `네트워크`라는 탭이 있을 뿐, 영상이 어떻게
들어오는지 화면 어디에도 쓰여 있지 않았다. 그것은 해보면서 알아낼 일이 아니다.
영상을 넣는 두 가지 방법(파일 앱, 같은 네트워크의 서버)이 모두 글레이즈 **바깥에서**
시작하기 때문이다.

- **첫 실행 카드** (`IOSWelcomeView`): 네 줄 — 영상 넣기, NAS, 자막, 손동작 — 과
  "영상은 이 기기 밖으로 나가지 않는다"는 한 문장. 넘겨야 하는 슬라이드가 아니라
  한 화면이고, `시작하기` 하나로 끝난다
- **손동작 안내** (`IOSGestureGuideView`): 처음 연 영상 위에 한 번. 더블탭·스와이프·
  길게 누르기·막대 끌기는 화면에 흔적을 남기지 않는 동작이라 — 그래서 좋은 동작이고,
  그래서 아무도 발견하지 못한다 — 글로 한 번은 말해야 한다. **읽는 동안 영상은 0초에
  멈춰 기다린다.** 안내를 읽는 사이에 오프닝이 지나가면 안내가 아니라 방해다
- **설정 › 도움말**: 둘 다 다시 볼 수 있다. 한 번만 볼 수 있는 안내는 안 쓴 것과 같다

문구는 `ios.welcome.*`, `ios.guide.*`, `ios.settings.help*` (한/영).

### 남은 것 — 재생 화면 위쪽이 가장 혼잡하다

오른쪽에 원형 버튼이 다섯~일곱 개 붙어 있고, 성격이 셋으로 갈린다.

| 묶음 | 버튼 |
|---|---|
| 화면 상태 | 잠금, 채우기/맞추기, 가로/세로 |
| 재생 | 배속(1×), 재생목록 |
| 내용 | 자막·음성 |

(`captions.bubble`)이 여는 것은 이름이 `ios.player.settings`인 시트다. 아이콘은 자막이라
말하고 이름은 설정이라 말한다.

제안(아직 구현 안 함):
- 화면 상태 세 개는 하나의 `…` 메뉴로 접는다. 영상을 보는 동안 자주 쓰는 것이 아니다
- 위쪽에 남는 것은 닫기 · 배속 · 자막 세 개
- 자막 버튼의 이름을 자막으로 맞춘다
- **재생 화면에서 영상 정보로 가는 길**도 이 메뉴에 넣는다 (`docs/49`의 남은 것)

## 5. 검증 중 발견한 결함 — 막대를 천천히 끌면 2배속이 걸린다

> **2026-10-08 갱신.** 첫 수정은 듣지 않았고, 그것을 **단언이 놓쳤다.**
> 아래 첫 수정은 `isScrubbing`을 보고 길게 누르기를 막는 방식이었는데, 막대의 드래그와
> 길게 누르기는 **같은 터치에서 시작**하므로 아래 레이어가 어느 쪽을 먼저 듣는지는
> 우리가 정할 수 있는 것이 아니다.
> 더 나쁜 것은 테스트였다. 손을 뗀 **뒤에** 배속 표시를 찾았는데, 그때는 이미
> `releaseHold()`가 지워 놓은 뒤라 버그가 화면에 그대로 떠 있어도 통과했다.
> 실제로 등록 이미지를 찍다가 `2× 속도`가 섬네일과 **나란히 찍힌 것**을 보고 알았다.
>
> **지금 고친 방식:** 컨트롤이 떠 있는 동안에는 화면 아래 170pt — 조작 막대와 재생
> 막대가 차지하는 띠 — 에서 시작한 누름은 길게 누르기로 치지 않는다. 손가락이 어디에
> 닿았는지는 두 제스처 중 무엇이 먼저 시작하든 상관없이 알 수 있다.
>
> **테스트도 고쳤다.** 끄는 도중에 다른 큐에서 화면을 읽는다. 손을 뗀 뒤에 보는 검사는
> 이 버그를 영원히 못 잡는다.



등록 이미지용 캡처에서 섬네일과 `2× 속도` 표시가 **동시에** 찍혔다. 터치 레이어가
화면 전체 높이를 차지하고 조작 막대 아래에도 깔려 있어서, 재생 막대를 천천히 끄는
동작이 "좌·우 길게 누르기"로도 읽힌다. 장면을 찾는 중에 영상이 2배속으로 달리면
플레이어가 사용자와 싸우는 것이다.

고침: 끄는 중(`isScrubbing`)에는 길게 누르기를 시작하지 않고, 손가락이 막대에
닿는 순간 이미 걸려 있던 배속은 푼다. **빌드는 통과했으나 화면으로 재확인하지는
못했다** — 다음 실기기 테스트에서 확인할 것.

## 부록. 실기기 검증 (2026-10-08, 아이폰 17 Pro, 빌드 14)

### 실기기를 조작하는 방법

`devicectl`은 화면을 **찍을 수는 있어도 만질 수는 없다** — `device capture screenshot`은
있고 입력 명령은 없다. 그래서 UI 테스트 타깃(`Tests/GlazeiOSUITests`)을 만들었다.
맥에서 `xcodebuild test`로 실제 폰을 조작하고, 각 단계의 스크린샷을 결과 번들에서
꺼낸다. 릴리스 빌드에 영향이 없도록 `GlazeiOS` 스킴이 아니라 별도 스킴에 둔다.

첫 빌드에는 `-allowProvisioningUpdates -allowProvisioningDeviceRegistration`이 필요하다
(기기가 개발자 계정에 등록되어 있지 않다).

### 테스트는 사용자의 영상을 열지 않는다

처음 쓴 테스트는 폴더의 **첫 번째 영상을 자동으로 열었고**, 그것은 기기 주인의 개인
영상이었다. 스크린샷에 그대로 찍혔고 전부 즉시 폐기했다.

지금은 테스트가 **직접 기기에 넣은 파일 하나만** 연다.

```bash
xcrun devicectl device copy to --device <기기> --domain-type appDataContainer \
  --domain-identifier com.edwin.glaze \
  --source "test file/testmedia.mkv" --destination Documents/glaze-uitest-sample.mkv
```

그 이름의 행이 없으면 테스트는 실패하고 끝난다. 찾아 들어가지 않는다.
네트워크 테스트는 서버 안의 파일을 열 수밖에 없으므로 **스크린샷을 한 장도 남기지
않는다.** 시간과 크래시 여부만 기록한다.

### 끄는 중의 화면을 찍는 법

제스처는 끝날 때까지 테스트 스레드를 붙잡는다. XCUITest가 찍는 스크린샷은 손가락을
뗀 **뒤**에 찍히고, 그때는 섬네일이 이미 사라져 있다 — 이 기능을 확인할 수 없었던
이유다. 맥에서 `devicectl`로 동시에 찍는 방법도 두 번 실패했다(타이밍이 맞지 않고
폰이 잠들었다).

해법은 제스처를 시작하기 **전에** 다른 큐에 스크린샷을 예약하는 것이다. 테스트
스레드는 끌고 있고, 예약된 쪽은 화면만 읽는다.

### 결과

| 항목 | 결과 |
|---|---|
| 첫 실행 카드 | 정상. `시작하기`로 닫히고 목록으로 |
| NEW 표시 | 줄 맨 앞 고정 칸 |
| 손동작 안내 | 첫 영상 위에 뜨고 영상은 0:00에서 대기. 닫으면 재생 시작 |
| **재생 막대 섬네일** | **실기기에서 확인.** 끄는 동안 28:29 지점의 실제 장면과 시간이 보인다 |
| **막대를 천천히 끌 때 2배속** | **해결 확인.** 끄는 동안 배속 표시가 뜨지 않음을 단언하고 통과 |
| 영상 정보 — 밀기 | 호박색 `영상 정보`가 나오고 화면이 열린다 |
| **TMDB 검색** | **실기기에서 동작.** 기기에 들어 있는 키로 `Parasite` 검색 → 후보 여러 개 |
| NAS 첫 폴더 목록 | 5.7초 / 5.6초 (두 번) |
| NAS 재생 시작 | 2.1초 |
| NAS 10초 이동 8회 | 한 번의 실행에서 앱이 죽지 않음 |

### 막힌 것 — 자동 잠금

폰이 1분 남짓마다 잠긴다. 잠기면 테스트 러너의 연결이 끊어지고
(`The connection was invalidated`), `devicectl`도 거부한다
(`not able to fulfill the requested usage assertion requirements`).
NAS 테스트 세 번 중 두 번이 이것으로 끝났다.

**설정 › 디스플레이 및 밝기 › 자동 잠금 → 안 함**으로 두고 실행해야 한다.

### 거짓 통과 두 건 — 단언을 고쳤다

- TMDB 테스트가 검색어 칸을 비우지 못해 `glaze-uitest-sampleParasite`를 검색했고,
  당연히 아무것도 찾지 못했다. 그런데 `검색 결과` 머리말은 **결과가 없어도 뜨므로**
  테스트는 통과했다. 지금은 "맞는 작품을 찾지 못했습니다"가 없을 것과 후보가 둘 이상일
  것을 함께 확인한다
- NAS 테스트가 "이동 뒤 재생 화면이 사라졌다"로 실패했는데, 컨트롤이 5초 뒤 스스로
  사라진 것이었다. 앱은 멀쩡했다. 지금은 컨트롤을 다시 부른 뒤 **재생 위치가 실제로
  움직였는지**까지 확인한다

### 등록 이미지

실기기는 6.3형 **1206×2622**다. 앱 스토어가 요구하는 아이폰 크기는 6.9형
**1320×2868**이라 실기기 캡처로는 규격을 맞출 수 없다. 같은 코드의 6.9형
시뮬레이터로 찍어야 한다. 그리고 등록 이미지에 쓸 영상은 CC 라이선스 작품이 따로
필요하다(위 3절).

## 부록 2. 테스트 기기와 베타 OS (2026-10-08)

### 베타 OS는 개발자 모드를 막지 않는다

확인한 사실이다. 추측이 아니라 세 기기에 실제로 물어본 결과다.

| 기기 | OS | 개발자 모드 | 결과 |
|---|---|---|---|
| 아이폰 17 Pro | 27.0.1 (24A446) 정식 | 켜짐 | 빌드·설치·UI 테스트 전부 동작 |
| 아이패드 미니 | **27.2 (24B5089g) 베타** | — | **빌드·설치·UI 테스트 전부 동작** |
| 아이폰 13 mini | **27.2 (24B5099f) 베타** | **꺼짐** | `The operation failed because Developer Mode is turned off.` |

13 mini가 안 되는 이유는 베타라서가 아니라 **토글이 꺼져 있어서**다. 같은 27.2
베타인 아이패드는 멀쩡히 동작한다. 베타에서도 개발자 모드 항목은 그대로 있다.

**13 mini를 쓰려면:** 설정 › 개인정보 보호 및 보안 › 개발자 모드 → 켬 → 재시동.
(항목이 안 보이면 기기를 맥에 연결한 채 Xcode로 한 번 빌드를 시도하면 나타난다.)

### 베타에서 실제로 문제가 되는 것

개발자 모드가 아니라 **Xcode 버전**이다. 이 맥의 Xcode는 27.0이고 iOS SDK도 27.0인데
두 기기는 27.2 베타다. 이번에는 설치와 UI 테스트가 모두 통과했지만, 기기가 Xcode보다
많이 앞서 나가면 개발자 디스크 이미지를 못 올려서 `device support` 오류가 난다.
그때는 같은 세대의 Xcode 베타가 필요하다.

**테스트플라이트로만 받아 볼 때는 아무 상관이 없다.** 개발자 모드도, Xcode 버전도
필요 없다.

### 처음 쓰는 기기는 계정에 등록해야 한다

새 기기로 바꾸면 첫 빌드에서 이렇게 멈춘다.

```
error: Device "..." isn't registered in your developer account.
```

`-allowProvisioningUpdates -allowProvisioningDeviceRegistration` 두 개를 함께 주면
Xcode가 등록하고 프로파일을 다시 받는다. 아이패드도 이 두 개로 해결했다.

### 아이패드 레이아웃 — 가로에서 비어 보인다

아이패드 미니 가로에서 탭 막대가 화면 **위쪽 알약**으로 올라가고, 목록은 화면 폭
전체를 쓴다. 폴더 두 개짜리 목록이 951pt를 가로지르고 오른쪽 끝에 화살표가 하나 있는
모양이라, 읽는 눈이 가로로 너무 멀리 간다. 아이패드의 관용은 사이드바 + 상세
(`NavigationSplitView`)다. 맥은 이미 그렇게 되어 있다.

이번 출시를 막는 문제는 아니지만 아이패드 사용성 항목으로 남긴다.

### 함정 — 아이패드의 XCUITest 스크린샷은 영상을 담지 못한다

아이패드에서 `XCUIScreen.screenshot()`이 돌려주는 그림은 영상 영역이 **새까맣다.**
재생은 멀쩡히 되고 있는데도 그렇다. VLC가 그리는 레이어를 테스트의 캡처가 보지
못한다. 처음에는 "아이패드에서 영상이 안 나온다"고 판단했는데,
`devicectl device capture screenshot`으로 **실제 프레임버퍼**를 찍어 보니 화면도
섬네일도 정상이었다. 아이폰에서는 같은 API가 영상을 담는다.

영상이 어떻게 보이는지에 대한 판단은 **devicectl 캡처로만** 한다. 테스트 첨부
스크린샷으로 판단하면 안 된다.

### 두 기기에 없는 것은 버그가 아니다

저장한 서버와 TMDB 키는 **그 기기의 설정과 키체인에** 있다. 새 기기는 비어 있고,
그것은 밖에서 보면 "서버에 연결되지 않는다"와 똑같아 보인다.

처음 쓴 NAS 테스트는 서버가 없는 아이패드에서 `새 서버` 버튼을 눌러 놓고 60초 동안
폴더 목록을 기다렸다. 세 번 연속 "서버를 열었으나 목록이 오지 않았다"로 실패했지만
열린 적이 없었다. 지금은 `아직 추가한 서버가 없습니다`를 먼저 보고 건너뛴다.
TMDB도 `키를 먼저 넣어야 합니다`를 보고 건너뛴다.

## 부록 3. 네트워크 재생 불안정 — 원인을 좁혔다 (2026-10-08)

아이패드 미니 · iPadOS 27.2 베타 · 서버의 `#1. 드라마` 폴더(기기 주인이 테스트용으로
표시해 둔 곳)에서 재현했다.

### 증상

**이어볼 지점이 생긴 네트워크 영상은 그 다음부터 열리지 않는다.**

같은 파일, 같은 실행, 같은 서버에서:

| | 결과 |
|---|---|
| 1회차 — 이어볼 지점 없음 | **2.1초** |
| 2회차 — 12초 보고 닫은 뒤 | **90초 안에 안 열림** |

폴더 목록은 내내 2.0~2.3초로 멀쩡했다. 서버도 네트워크도 아니다. 화면은 **목록에
그대로 머물고 재생 화면이 아예 뜨지 않는다** — 느리게 열리는 것이 아니라 열리지
않는다.

### 좁혀 간 과정 (틀린 길 포함)

1. 같은 테스트를 다섯 번 돌렸더니 1회차만 통과하고 2~5회차가 전부 90초 초과.
2. "이어보기 때문"이라 보고 재생 위치를 지우려 했으나, 목록 행을 길게 눌러도
   **아이패드에서는 컨텍스트 메뉴가 열리지 않아서**(`app.menuItems`가 빈 배열)
   지우지 못했다. 그런데 테스트는 "지울 위치가 없었다"고 찍고 **그대로 진행**해,
   확인하려던 조건을 확인하지 않은 채 실패했다.
3. 대신 한 번도 재생한 적 없는 영화를 열었더니 2.2초. 같은 영화를 또 열어도 2.2초라
   **이어보기 가설이 틀린 줄 알았다.**
4. 화면을 실제로 찍어 보니 그 영화에는 애초에 이어볼 지점이 없었다. 목록에서 진행
   막대가 붙은 것은 S01E01 하나뿐이고 나머지 다섯 개는 전부 NEW 점이었다. **서로 다른
   파일을 비교하고 있었다.**
5. 한 파일로 1회차·2회차를 한 실행 안에서 비교하게 고쳤다. 위 표가 그 결과다.

### 아직 모르는 것

재생 화면이 왜 **뜨지도 않는지**. `startAt`이 0이 아닐 때만 다른 점은
`IOSPlaybackModel.start`의 `pendingResume`과 `applyResumeIfReady()`의 `seek(to:)`인데,
그 seek은 재생이 시작된 뒤에야 돌아가므로 화면이 뜨지 않는 것을 설명하지 못한다.
libVLC 호출이 메인 스레드를 잡고 있어 화면이 그리지 못하는 쪽이 더 그럴듯하다.

**다음 단계:** 멈춘 동안 기기 콘솔 로그를 받아 VLC가 무엇을 하고 있는지 본다.
추측으로 고치지 않는다.
