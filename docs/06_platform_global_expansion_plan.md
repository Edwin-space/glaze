# 플랫폼 및 글로벌 확장 계획

작성일: 2026-06-18  
최종 수정: 2026-08-10 (기초 재설계 결정 반영, 근거: `16_foundation_redesign_audit.md`)  
프로젝트명: 글레이즈

## 문서 목적

이 문서는 글레이즈의 플랫폼 확장과 글로벌 제공 전략을 정리한다. 초기에는 macOS Apple Silicon 앱으로 시작하되, 이후 스마트폰 OS, Windows 제품군, 글로벌 다국어 서비스로 확장하는 순서를 정의한다.

현재 계획은 확정된 개발 범위가 아니라 제품 방향성이다. 실제 구현 순서는 MVP 성과, AI 모델 성능, 비용 구조, 앱스토어 정책, 사용자의 반응에 따라 조정한다.

## 기본 판단

글레이즈는 처음부터 모든 플랫폼을 동시에 지원하면 안 된다. 핵심 기능이 온디바이스 AI 자막 생성과 영상 재생 품질에 걸려 있기 때문에, 성능과 사용자 경험을 가장 통제하기 쉬운 플랫폼에서 먼저 증명해야 한다.

초기 최적 플랫폼은 macOS Apple Silicon이다.

이유:

- Apple Silicon의 온디바이스 AI 성능을 직접 활용하기 좋다.
- 영상 파일, 자막 파일, 외장 디스크, NAS 같은 개인 미디어 사용성이 데스크톱에서 더 자연스럽다.
- 긴 영상의 사전 자막 생성, 배치 처리, 백그라운드 큐가 모바일보다 적합하다.
- Submarine Player 같은 직접 레퍼런스도 Apple Silicon/macOS 중심으로 시장 검증을 하고 있다.
- 초기 개발 범위를 좁히면 플레이어 품질과 AI 자막 품질에 집중할 수 있다.

## 권장 확장 순서

### Phase A. macOS Apple Silicon

초기 제품은 macOS Apple Silicon 전용 또는 우선 지원으로 시작한다.

목표:

- 로컬 영상 플레이어 MVP 완성
- 단일 영상 AI 자막 생성
- 한국어 번역 자막
- 생성 자막 저장과 자동 연결
- 재생목록/라이브러리 기반 자막 준비
- 브라우저 확장 연동 실험

이 단계의 핵심은 "글레이즈가 왜 필요한가"를 증명하는 것이다. 포맷 지원이나 부가 기능보다 자막 없는 영상을 실제로 볼 수 있게 만드는 경험을 완성해야 한다.

### Phase B. iOS/iPadOS 보조 앱

실제 iPhone/iPad 앱 출시는 macOS MVP가 안정화된 뒤 검토한다. 다만 이 순서는 제품 출시 시점에 한정된다 — 아키텍처는 다르다.

Apple Silicon 온디바이스 AI(Core ML/Neural Engine)를 macOS와 iOS 양쪽에서 활용하는 것이 제품 계획에 들어오면서, `GlazeCore`(플랫폼 독립: 미디어 자산 모델, 자막 파싱, AI 자막/번역 엔진 인터페이스, Job Queue)와 `GlazeMac`(macOS 전용: AppKit/AVKit/VLC 재생 표면)의 모듈 분리는 지금 macOS 개발 단계에서부터 반영한다. "지금 iOS 앱을 만든다"는 뜻이 아니라 "지금 짜는 구조가 iOS 확장을 막지 않아야 한다"는 뜻이다. 모바일 앱은 macOS 앱을 그대로 복제하면 안 된다.

> **2026-08-10 갱신**: `GlazeCore`는 이제 `Packages/GlazeCore`의 독립 SwiftPM 로컬 패키지이고, macOS 앱 자체도 XcodeGen(`project.yml`)이 생성하는 정식 Xcode 프로젝트로 전환됐다(자세한 내용은 `Tools/README.md`). 이후 iOS(그리고 Phase E의 Apple TV)를 실제로 시작할 때는 `project.yml`에 새 앱 타겟을 추가하고 동일한 `Packages/GlazeCore`를 의존성으로 연결하면 된다 — 지금 당장 그 타겟을 만들어두지는 않았다.

모바일의 자연스러운 역할:

- macOS에서 생성된 자막과 라이브러리 상태 확인
- 자막이 준비된 영상을 모바일에서 재생
- 원문/한국어 이중 자막 감상
- 짧은 영상의 온디바이스 자막 생성
- iCloud 또는 계정 기반 동기화
- AirPlay와 거실 감상 연결
- 외국어 학습 모드

모바일에서 조심해야 할 점:

- 긴 영상의 AI 자막 생성은 배터리와 발열 부담이 크다.
- 백그라운드 처리가 OS 정책상 제한될 수 있다.
- 로컬 파일 접근과 다운로드/저장 UX가 데스크톱보다 복잡하다.
- App Store 심사에서 다운로드, 웹 영상 처리, 백그라운드 작업 설명이 중요하다.

따라서 스마트폰 OS 확장은 "모바일에서도 모든 것을 생성한다"보다 "macOS에서 준비된 자막 경험을 이어서 본다"로 시작하는 것이 안전하다.

### Phase C. Android 검토

글로벌 확장을 고려하면 Android는 중요하지만, 초기에는 iOS보다 뒤로 둔다.

이유:

- 기기 성능 편차가 크다.
- 온디바이스 AI 모델 최적화와 배포 난이도가 높다.
- 영상 코덱, 파일 접근, 백그라운드 정책이 제조사별로 달라질 수 있다.
- 결제와 구독 관리가 별도 체계가 된다.

Android는 다음 조건이 갖춰졌을 때 검토한다.

- 자막 생성 엔진이 플랫폼 독립적으로 분리됨
- 서버/클라우드 또는 경량 온디바이스 모델 운영 전략이 정리됨
- 글로벌 사용자가 모바일 수요를 명확히 보임
- macOS/iOS에서 유료화와 유지율이 검증됨

### Phase D. Windows 데스크톱

Windows는 시장 규모가 크고 글로벌 확장에 중요하다. 다만 초기에는 macOS보다 뒤에 둔다.

Windows 확장의 장점:

- 전 세계 데스크톱 사용자 기반이 크다.
- 로컬 영상, 다운로드 영상, NAS/외장 저장장치 사용성이 좋다.
- 배치 자막 생성과 라이브러리 관리가 데스크톱 UX에 잘 맞는다.
- GPU 가속, ONNX Runtime, DirectML 같은 선택지가 있다.

Windows 확장의 어려움:

- 하드웨어 편차가 크다.
- 드라이버/GPU/코덱 환경이 다양하다.
- 설치/업데이트/보안 경고/백신 오탐 같은 운영 이슈가 생길 수 있다.
- Apple Silicon 중심으로 만든 AI 파이프라인을 재설계해야 할 수 있다.

Windows는 macOS에서 제품 가치가 검증된 뒤, "글레이즈 데스크톱 제품군"의 두 번째 핵심 플랫폼으로 확장하는 것이 좋다.

### Phase E. Apple TV / NAS 미디어 경험

Apple TV 앱과 NAS/자체 미디어 서버는 장기 프리미엄 확장의 핵심 후보로 둔다. macOS 앱이 자막 생성, 번역, 메타데이터 정리의 중심이 되고, Apple TV는 거실 감상 앱으로 시작한다.

목표:

- macOS에서 준비한 자막과 메타데이터를 Apple TV에서 감상
- iCloud 또는 계정 기반 시청 위치 동기화
- NAS/SMB/WebDAV 또는 자체 서버 라이브러리 스캔
- Plex처럼 포스터/시즌/에피소드 기반 탐색 제공
- AI 자막 준비 상태를 거실 화면에서도 확인

## 플랫폼별 제품 역할

| 플랫폼 | 1차 역할 | 권장 시점 | 핵심 기능 |
|---|---|---|---|
| macOS Apple Silicon | 주력 생성/재생 앱 | 초기 | AI 자막 생성, 번역, 라이브러리, 배치 처리 |
| iOS/iPadOS | 보조 감상/동기화 앱 | macOS 안정화 이후 | 자막 준비된 영상 재생, 학습, 간단 생성 |
| Android | 글로벌 모바일 확장 | iOS 이후 검토 | 모바일 감상, 학습, 경량 생성 |
| Windows | 글로벌 데스크톱 확장 | 제품 가치 검증 이후 | 데스크톱 재생, 배치 생성, 라이브러리 |
| 브라우저 확장 | 웹 영상 브릿지 | MVP 이후 실험 | DRM 없는 웹 영상 열기, HLS 감지 |
| Apple TV | 거실 감상 앱 | 라이브러리/동기화 이후 | 자막 준비된 영상 재생, 이어보기 |
| NAS/서버 | 프리미엄 라이브러리 확장 | macOS 라이브러리 검증 이후 | 라이브러리 스캔, 메타데이터, 기기 연속성 |

## 글로벌 제공 전략

글레이즈는 한국 사용자에서 출발하되, 제품 자체는 글로벌 시장을 목표로 한다.

초기 기본 UI 언어:

- 한국어
- 영어

한국어는 초기 사용자의 기본 경험을 위해 중요하고, 영어는 글로벌 확장, App Store/웹사이트/문서/고객지원의 기준 언어가 된다.

이후 중요 국가별 확장 언어:

- 일본어
- 중국어 간체
- 중국어 번체
- 스페인어
- 프랑스어
- 독일어
- 포르투갈어
- 베트남어
- 인도네시아어
- 태국어

언어 확장은 한 번에 많이 추가하기보다, 실제 유입 국가와 결제 전환을 보고 우선순위를 조정한다.

## 번역 운영 방식

초기에는 번역기를 활용한 다국어 UI 번역을 사용할 수 있다. 다만 제품의 핵심 화면은 반드시 사람이 검수해야 한다.

권장 방식:

1. 한국어와 영어는 직접 작성한다.
2. 다른 언어는 기계 번역으로 초안을 만든다.
3. 결제, 개인정보, 오류, 권한, 다운로드, DRM 관련 문구는 사람이 검수한다.
4. 자주 쓰이는 UI 문구는 용어집으로 관리한다.
5. 앱 내 번역 품질 제보 기능을 둔다.

특히 자막/번역/DRM/다운로드 관련 문구는 오해가 생기면 정책 리스크가 커지므로 자동 번역만으로 배포하지 않는다.

## 제품 구조에 미리 반영할 것

플랫폼 확장은 나중이지만, 아래 구조는 지금 macOS 개발 단계부터 실제로 적용한다(더 이상 "고려 사항"이 아니라 아키텍처 전제다).

- `Package.swift`를 `GlazeCore`(플랫폼 독립 라이브러리 타겟)와 `GlazeMac`(macOS 전용 executable 타겟)으로 분리
- UI 문자열 분리와 localization 파일 관리
- 자막 생성 엔진과 UI의 분리 — `GlazeCore`에 위치
- 자막 포맷 처리 모듈의 플랫폼 독립화
- 작업 큐와 라이브러리 데이터 모델의 이식 가능성 — `GlazeCore`에 위치
- AI 자막 생성/번역 파이프라인(Core ML 기반)은 처음부터 `GlazeCore`에 두고 macOS/iOS 양쪽에서 공유
- VLC/libVLC 네이티브 재생 엔진은 macOS 전용이므로 `GlazeMac`에 격리(iOS는 AVFoundation/AVKit이 기본 경로가 될 가능성이 높음)
- 계정/동기화 도입 가능성을 고려한 데이터 구조
- `MediaAsset` 기반 파일/메타데이터/자막/시청 위치 분리
- 원본 파일 수정과 sidecar metadata 저장 정책 분리
- 플랫폼별 기능 플래그
- 다운로드/브라우저 확장 기능의 정책별 on/off 구조

## 내 의견

가장 좋은 순서는 다음과 같다.

1. macOS Apple Silicon에서 글레이즈의 핵심 가치를 완성한다.
2. 글로벌을 고려해 처음부터 한국어/영어 UI와 문서 구조로 만든다.
3. macOS에서 자막 생성/번역/라이브러리 준비 경험이 검증되면 iOS/iPadOS를 보조 감상 앱으로 확장한다.
4. 모바일에서 무리하게 긴 영상 생성까지 욕심내지 말고, 준비된 자막을 이어보는 경험부터 만든다.
5. 이후 글로벌 사용량과 수익성이 확인되면 Windows 데스크톱을 확장한다.
6. Android는 글로벌 모바일 수요가 명확해진 뒤, 엔진과 비용 구조가 안정됐을 때 진입한다.

즉, 글레이즈의 초기 정체성은 "macOS AI 자막 플레이어"이고, 장기 정체성은 "개인 영상 라이브러리를 모든 기기에서 자막화하고 감상하게 해주는 글로벌 AI 미디어 플랫폼"이다.
