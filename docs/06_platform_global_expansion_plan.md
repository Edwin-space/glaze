# 플랫폼 및 글로벌 확장 계획

작성일: 2026-06-18  
최종 수정: 2026-08-28 (Apple 플랫폼 설정 동기화 경계 반영)
프로젝트명: 글레이즈

## 문서 목적

이 문서는 글레이즈의 플랫폼 확장과 글로벌 제공 전략을 정리한다. 초기에는 macOS Apple Silicon 앱으로 시작하되, 이후 스마트폰 OS, Windows 제품군, 글로벌 다국어 서비스로 확장하는 순서를 정의한다.

현재 계획은 확정된 개발 범위가 아니라 제품 방향성이다. 실제 구현 순서는 MVP 성과, AI 모델 성능, 비용 구조, 앱스토어 정책, 사용자의 반응에 따라 조정한다.

## 기본 판단

글레이즈는 처음부터 모든 플랫폼을 동시에 지원하면 안 된다. 핵심 기능이 온디바이스 AI 자막 생성과 영상 재생 품질에 걸려 있기 때문에, 성능과 사용자 경험을 가장 통제하기 쉬운 플랫폼에서 먼저 증명해야 한다.

초기 최적 플랫폼은 macOS Apple Silicon이다.

이유:

- Apple Silicon의 온디바이스 AI 성능을 직접 활용하기 좋다.
- 영상 파일, 자막 파일, 외장 디스크, NAS 같은 개인 미디어 사용성이 데스크톱에서 더 자연스럽다.
- 긴 영상의 사전 자막 생성, 배치 처리, 백그라운드 큐가 모바일보다 적합하다.
- Submarine Player 같은 직접 레퍼런스도 Apple Silicon/macOS 중심으로 시장 검증을 하고 있다.
- 초기 개발 범위를 좁히면 플레이어 품질과 AI 자막 품질에 집중할 수 있다.

## 우선순위 재조정 (2026-08-20 확정)

크로스플랫폼 구축을 유료화·외부 LLM보다 앞에 둔다. 근거: **재생 경험은 플랫폼마다 새로 만들어야 하지만, 엔진 교체와 유료화는 나중에 macOS 한 곳만 손대면 되는 일**이다. 기반이 여러 기기에 깔린 뒤에 얹는 편이 순서상 자연스럽다.

예외는 Foundation Models 번역 엔진이다. 이것은 확장 기능이 아니라 **현재 번역 품질의 결함을 메우는 작업**이라 v1.0에 포함한다 — 시스템 번역은 문자열 in/out이라 한국어 말투를 지정할 방법이 없고, 그 결과 한 편 안에서 문체가 뒤섞인다(`03_ai_subtitle_workflow.md`). 다운로드도 라이선스 리스크도 없고 macOS 안에서 끝나므로 크로스플랫폼 작업과 경쟁하지 않는다.

| 버전 | 내용 |
|---|---|
| **v1.0** | macOS 출시 — 재생·자막 생성·번역이 끊김 없이 동작 **+ Foundation Models 번역 엔진** |
| **v1.1** | **Apple TV + NAS 거실 감상** (기존 v3에서 상향) |
| v1.2 | iOS/iPadOS |
| **v3** | **외부 LLM 창구, 유료화** (기존 v1.1~v1.2에서 하향) |

### 이 순서를 막는 것은 AI가 아니라 두 가지 macOS 전용 메커니즘이다

코드를 확인한 결과, 지금 macOS에서 쓰는 두 축이 iOS·tvOS에서 **원리적으로 동작하지 않는다.**

1. **`EmbeddedSubtitleService`가 `ffprobe`/`ffmpeg`를 서브프로세스로 실행한다.** iOS·tvOS는 앱이 외부 실행 파일을 띄우는 것을 금지한다. 내장 자막 감지·추출 경로 전체가 이식되지 않는다.
2. **`NativeVLCLibrary`가 `dlopen`으로 libvlc를 런타임 로드한다.** iOS·tvOS는 임의 dylib의 `dlopen`을 금지한다. 재생 엔진이 이식되지 않는다.

`GlazeCore`는 깨끗하다 — AppKit·`Process`·`dlopen` 의존이 없어 자막 모델, 파서, 문장 재조립, 번역 파이프라인은 그대로 재사용된다.

**대안:**

- 재생: iOS·tvOS는 AVFoundation을 우선으로 하고(H.264/HEVC MP4는 대부분 커버), 나머지 형식은 VideoLAN 공식 **VLCKit**(iOS·tvOS 지원, 정적 링크)으로 처리한다. `dlopen` 구조는 macOS에 남긴다.
- 내장 자막: AVAsset이 읽는 것은 AVFoundation으로, MKV 등은 VLCKit 또는 Swift 네이티브 파서로 대체한다. 또는 macOS에서 추출해 동기화한다.

이 두 가지가 v1.1·v1.2의 실제 작업량이며, AI보다 크다.

### iOS/iPadOS 온디바이스 AI — 가능하지만 제약은 성능이 아니다

뉴럴엔진 활용 자체는 문제없다. WhisperKit은 iOS를 지원하고 Core ML은 iOS·iPadOS에서 ANE를 쓴다. M시리즈 iPad는 사실상 Mac급이다. 실제 제약은 OS 정책 쪽이다.

- **백그라운드 실행이 가장 큰 벽이다.** 두 시간짜리 영화 전사는 수 분에서 수십 분이 걸리는데, iOS는 앱이 백그라운드로 내려가면 연산을 중단시킨다. 오디오 백그라운드 모드는 재생용이지 연산용이 아니고, `BGProcessingTask`는 시스템이 실행 시점을 정하므로(대개 충전 중 야간) "지금 만들어줘"에 대한 답이 되지 못한다.
- **메모리 한도.** iOS는 앱 메모리를 강제로 제한한다. large-v3(약 1.6GB)는 iPhone에서 무리고, 중간 단계도 구형 기기에서는 빠듯하다. iPad Pro는 여유가 있다.
- **발열 스로틀링.** iPhone은 지속 부하에서 빠르게 스로틀링된다. ANE를 10분 이상 밀면 속도가 급격히 떨어진다.
- **모델 다운로드.** 250MB~1.6GB를 셀룰러로 받게 해서는 안 된다. Wi-Fi 우선 다운로드가 필요하다.

따라서 이 문서가 원래 제시한 **"macOS에서 준비하고 iOS에서 이어서 본다"** 는 방향이 여전히 맞다. iOS에서의 생성은 짧은 클립이나 포그라운드를 유지하는 상황으로 한정하고, 긴 영상은 macOS에서 준비한 결과를 받아 보는 형태로 간다.

### 플랫폼별 역할 차별화 (2026-08-20 확정)

iOS·iPadOS에서 AI 생성을 직접 하지 않는다. 위의 제약(백그라운드 중단, 메모리 한도, 발열)을 우회하는 가장 정직한 방법이고, Infuse·VLC·nPlayer 같은 기존 제품도 같은 구조를 택한다.

| | macOS | iOS/iPadOS | tvOS |
|---|---|---|---|
| 역할 | 작업실 — 자막을 만든다 | 플레이어 — 만든 자막으로 본다 | 거실 — 본다 |
| AI 전사·번역 | ○ | ✕ | ✕ |
| 로컬 파일 | ○ | ○ (Files 반입) | **✕ 구조적으로 불가** |
| DLNA/UPnP | ○ 구현됨 | 추가 | 추가 |
| WebDAV | 추가 | 추가 | 추가 |
| 직접 HTTP/HLS URL | 추가 | 추가 | 추가 |
| SMB | **Finder 마운트로 이미 가능** | Files 앱에 위임 | ✕ |
| FTP | 제외 확정 | 제외 확정 | 제외 확정 |

#### tvOS에 로컬 파일이 없는 것은 제약이 아니라 전제다

Apple TV는 **저장장치용 USB 포트가 없다.** 구형 모델의 USB-C는 서비스·진단용이었고 현행 Apple TV 4K에는 포트 자체가 없다. 외장 드라이브를 꽂는 시나리오는 성립하지 않는다.

여기에 더해 tvOS는 **Files 앱도 문서 선택기도 없고**, 앱의 영구 저장 공간을 사용자 자료 보관용으로 쓰도록 설계되지 않았다(용량이 제한되고 시스템이 회수할 수 있는 캐시 성격이다). 즉 "사용자가 기기에 파일을 넣어둔다"는 개념이 tvOS에는 존재하지 않는다.

따라서 tvOS는 **처음부터 네트워크 전용**으로 설계한다. 감상 중 임시 캐싱은 가능하지만 라이브러리를 기기에 두는 형태는 불가능하다. 이 제약이 오히려 NAS/DLNA 경로를 tvOS의 핵심으로 만든다 — `18_embedded_subtitle_dlna_appletv_foundation.md`가 잡아둔 방향과 일치한다.

**자막 전달 경로가 플랫폼마다 다르다는 점에 주의한다.** 영상은 NAS에서 스트리밍하더라도 우리가 만든 자막은 기기에 도달해야 한다.

- iOS·iPadOS: iCloud Drive 문서 동기화로 처리 가능
- tvOS: **iCloud Drive 문서 접근이 없다.** CloudKit 프라이빗 DB를 써야 한다 — 구현 착수 전에 실제 가용성을 확인한다

#### macOS의 SMB는 이미 해결되어 있다

Finder가 SMB 공유를 마운트하면 `/Volumes` 아래 일반 파일 경로로 보이고, 현재 `NSOpenPanel` 기반 열기가 그대로 동작한다. **macOS용 SMB 클라이언트를 구현할 이유가 없다.**

**이미 이식 가능한 것**: `GlazeCore/NetworkMedia`(SSDP·ContentDirectory·DIDL-Lite 파싱)는 순수 Foundation이라 그대로 쓰인다. `SubtitleSidecarDetector`도 마찬가지다. SSDP 탐색 서비스만 현재 `GlazeMac`에 있는데 BSD 소켓 기반이라 iOS에서도 동작한다 — **`GlazeCore`로 옮기면 된다.**

#### 네트워크 프로토콜 — 무엇을 지원할 것인가

세 플랫폼 모두에 같은 세트를 넣는다. macOS도 DLNA 하나로 두지 않는다 — DLNA를 켜지 않은 NAS도 흔하고, DLNA의 미디어 라이브러리 뷰보다 폴더 그대로 보는 편이 나은 경우가 있다.

| 프로토콜 | 판단 | 근거 |
|---|---|---|
| DLNA/UPnP | **채택** | 이미 구현돼 있고 이식 가능 |
| WebDAV | **채택** | HTTP 기반이라 `URLSession`으로 처리되고, Range 요청이 되어 **탐색(seek)이 작동**한다. 시놀로지가 기본 지원 |
| 직접 HTTP/HLS URL | **채택** | AVFoundation이 그대로 처리 |
| SMB | **직접 구현하지 않는다** | iOS에 공개 SMB API가 없다. 직접 구현하면 라이선스·유지보수 부담이 크다. 대신 **iOS Files 앱이 SMB 연결을 지원하므로**, 사용자가 Files에서 SMB를 연결해두면 문서 선택기로 그 파일을 연다. 구현 없이 SMB를 지원하는 셈이다 |
| FTP | **제외 (2026-08-20 최종 확정)** | `CFFTPStream`이 사라졌고 직접 구현해야 하는데, Range 요청이 사실상 없어 미디어 탐색에 부적합하다 |

#### 파일 반입은 "앱 내부 저장"만으로 두지 않는다

앱 샌드박스 안에 넣는 방식은 옛 iTunes 파일 공유 모델이다. 두 가지를 함께 지원한다.

- **제자리 열기** — Files에서 직접 연다. iCloud, 마운트된 SMB 공유, iPad에 연결한 외장 드라이브가 전부 여기로 들어온다
- **앱으로 복사** — 오프라인 보관이 필요할 때

#### Mac에서 만든 자막을 어떻게 기기로 옮길 것인가

수동 복사에 맡기는 것이 이 구조의 가장 약한 고리다. `.mkv`를 아이폰에 옮기는 일은 번거롭고, 경쟁 제품이 이기는 지점이 정확히 여기다.

핵심은 **영상은 크지만 자막은 아주 작고, 자막이 우리가 만든 것**이라는 점이다.

- 영상은 NAS에 두거나 기기에 직접 넣게 둔다 (크고, 우리가 만든 것이 아니다)
- **자막만 iCloud Drive로 동기화한다.** 서버도 운영 비용도 없이 "Mac에서 만든 자막이 아이폰에 이미 있는" 경험이 된다
- 짝은 영상 파일명 기준으로 맞춘다 — `SubtitleSidecarDetector`가 이미 그 로직이다

v1.2 범위로 둔다. 수동 복사보다 경험이 훨씬 낫고 인프라 요구는 0이다.

#### 설정 동기화 계약 (2026-08-28)

macOS에서 만든 설정과 NAS 연결을 Apple TV·iPhone·iPad가 이어받을 수 있지만, 모든 값을 하나의 설정 파일로 동기화하지 않는다.

| 데이터 | 저장·동기화 | 이유 |
|---|---|---|
| 자막 크기·위치·배경, 선호 원문/번역 언어, 번역 출력 기본값 | `NSUbiquitousKeyValueStore` | 1MB 이하의 작은 환경 설정에 적합하고 같은 Apple 계정의 앱 인스턴스에서 공유 가능 |
| NAS 표시 이름·기본 URL·사용자 이름 | `NSUbiquitousKeyValueStore` | 비밀이 아닌 연결 메타데이터이며 플랫폼 공통 키로 표현 가능 |
| NAS 비밀번호·토큰 | 기기 Keychain | KVS에 비밀을 넣지 않는다. 특히 tvOS 앱 Keychain 항목은 iCloud Keychain으로 다른 기기와 동기화되지 않으므로 Apple TV에서 다시 입력하거나 향후 안전한 페어링을 제공한다 |
| 보안 범위 폴더 bookmark·SMB 마운트 경로 | 기기 로컬 | 접근 권한과 경로가 기기마다 다르다 |
| 모델 다운로드·캐시 상태 | 기기 로컬 | 기기 성능·용량·지원 엔진이 다르다 |
| 영상별 언어 교정·TMDB 매칭·이어보기 | CloudKit private database/CKSyncEngine 후보 | KVS보다 큰 구조화 데이터이며 충돌·증분 동기화가 필요하다 |

동일한 iCloud KVS 식별자와 안정된 locale 독립 키를 macOS/iOS/iPadOS/tvOS 타깃에서 공유한다. 현재는 배포 프로비저닝에 영향을 주지 않도록 iCloud entitlement를 켜지 않고 저장 계층 경계만 확정한다. 기능 구현 시 iCloud capability와 container를 App Store Connect 프로비저닝에 맞춰 한 번에 추가한다.

## 권장 확장 순서

### Phase A. macOS Apple Silicon

초기 제품은 macOS Apple Silicon 전용 또는 우선 지원으로 시작한다.

목표:

- 로컬 영상 플레이어 MVP 완성
- 단일 영상 AI 자막 생성
- 한국어 번역 자막
- 생성 자막 저장과 자동 연결
- 재생목록/라이브러리 기반 자막 준비
- 브라우저 확장 연동 실험

이 단계의 핵심은 "글레이즈가 왜 필요한가"를 증명하는 것이다. 포맷 지원이나 부가 기능보다 자막 없는 영상을 실제로 볼 수 있게 만드는 경험을 완성해야 한다.

### Phase B. iOS/iPadOS 보조 앱

실제 iPhone/iPad 앱 출시는 macOS MVP가 안정화된 뒤 검토한다. 다만 이 순서는 제품 출시 시점에 한정된다 — 아키텍처는 다르다.

Apple Silicon 온디바이스 AI(Core ML/Neural Engine)를 macOS와 iOS 양쪽에서 활용하는 것이 제품 계획에 들어오면서, `GlazeCore`(플랫폼 독립: 미디어 자산 모델, 자막 파싱, AI 자막/번역 엔진 인터페이스, Job Queue)와 `GlazeMac`(macOS 전용: AppKit/AVKit/VLC 재생 표면)의 모듈 분리는 지금 macOS 개발 단계에서부터 반영한다. "지금 iOS 앱을 만든다"는 뜻이 아니라 "지금 짜는 구조가 iOS 확장을 막지 않아야 한다"는 뜻이다. 모바일 앱은 macOS 앱을 그대로 복제하면 안 된다.

> **2026-08-10 갱신**: `GlazeCore`는 이제 `Packages/GlazeCore`의 독립 SwiftPM 로컬 패키지이고, macOS 앱 자체도 XcodeGen(`project.yml`)이 생성하는 정식 Xcode 프로젝트로 전환됐다(자세한 내용은 `Tools/README.md`). 이후 iOS(그리고 Phase E의 Apple TV)를 실제로 시작할 때는 `project.yml`에 새 앱 타겟을 추가하고 동일한 `Packages/GlazeCore`를 의존성으로 연결하면 된다 — 지금 당장 그 타겟을 만들어두지는 않았다.

모바일의 자연스러운 역할:

- macOS에서 생성된 자막과 라이브러리 상태 확인
- 자막이 준비된 영상을 모바일에서 재생
- 원문/한국어 이중 자막 감상
- 짧은 영상의 온디바이스 자막 생성
- iCloud 또는 계정 기반 동기화
- AirPlay와 거실 감상 연결
- 외국어 학습 모드

모바일에서 조심해야 할 점:

- 긴 영상의 AI 자막 생성은 배터리와 발열 부담이 크다.
- 백그라운드 처리가 OS 정책상 제한될 수 있다.
- 로컬 파일 접근과 다운로드/저장 UX가 데스크톱보다 복잡하다.
- App Store 심사에서 다운로드, 웹 영상 처리, 백그라운드 작업 설명이 중요하다.

따라서 스마트폰 OS 확장은 "모바일에서도 모든 것을 생성한다"보다 "macOS에서 준비된 자막 경험을 이어서 본다"로 시작하는 것이 안전하다.

### Phase C. Android 검토

글로벌 확장을 고려하면 Android는 중요하지만, 초기에는 iOS보다 뒤로 둔다.

이유:

- 기기 성능 편차가 크다.
- 온디바이스 AI 모델 최적화와 배포 난이도가 높다.
- 영상 코덱, 파일 접근, 백그라운드 정책이 제조사별로 달라질 수 있다.
- 결제와 구독 관리가 별도 체계가 된다.

Android는 다음 조건이 갖춰졌을 때 검토한다.

- 자막 생성 엔진이 플랫폼 독립적으로 분리됨
- 서버/클라우드 또는 경량 온디바이스 모델 운영 전략이 정리됨
- 글로벌 사용자가 모바일 수요를 명확히 보임
- macOS/iOS에서 유료화와 유지율이 검증됨

### Phase D. Windows 데스크톱

Windows는 시장 규모가 크고 글로벌 확장에 중요하다. 다만 초기에는 macOS보다 뒤에 둔다.

Windows 확장의 장점:

- 전 세계 데스크톱 사용자 기반이 크다.
- 로컬 영상, 다운로드 영상, NAS/외장 저장장치 사용성이 좋다.
- 배치 자막 생성과 라이브러리 관리가 데스크톱 UX에 잘 맞는다.
- GPU 가속, ONNX Runtime, DirectML 같은 선택지가 있다.

Windows 확장의 어려움:

- 하드웨어 편차가 크다.
- 드라이버/GPU/코덱 환경이 다양하다.
- 설치/업데이트/보안 경고/백신 오탐 같은 운영 이슈가 생길 수 있다.
- Apple Silicon 중심으로 만든 AI 파이프라인을 재설계해야 할 수 있다.

Windows는 macOS에서 제품 가치가 검증된 뒤, "글레이즈 데스크톱 제품군"의 두 번째 핵심 플랫폼으로 확장하는 것이 좋다.

### Phase E. Apple TV / NAS 미디어 경험

Apple TV 앱과 NAS/자체 미디어 서버는 장기 프리미엄 확장의 핵심 후보로 둔다. macOS 앱이 자막 생성, 번역, 메타데이터 정리의 중심이 되고, Apple TV는 거실 감상 앱으로 시작한다.

목표:

- macOS에서 준비한 자막과 메타데이터를 Apple TV에서 감상
- iCloud 또는 계정 기반 시청 위치 동기화
- NAS/SMB/WebDAV 또는 자체 서버 라이브러리 스캔
- Plex처럼 포스터/시즌/에피소드 기반 탐색 제공
- AI 자막 준비 상태를 거실 화면에서도 확인

2026-08-27 기반 작업:

- `GlazeCore`에 로컬/네트워크 미디어를 통합하는 `MediaResource`와 DLNA 서버·컨테이너·영상 모델을 추가했다.
- SSDP M-SEARCH 응답, UPnP Device Description, ContentDirectory SOAP Browse, DIDL-Lite 파싱을 플랫폼 공통 계층으로 분리했다.
- macOS에 동일 네트워크의 MediaServer 탐색 서비스와 원격 HTTP URL의 VLC 재생 경로를 추가했다.
- 내장 텍스트 자막의 언어 선택·추출·표시 및 번역 입력 계획을 공통 모델로 분리했다.
- `GlazeTV` 타깃과 focus engine 기반 NAS 탐색 UI를 추가했고, DLNA 자동 탐색과 WebDAV 수동 연결을 같은 감상 흐름으로 제공한다.
- VLCKit 정적 링크 재생, WebDAV sidecar 자막 선택, 미디어 서버 관례의 언어 코드 자막 파일명까지 시뮬레이터에서 검증했다.
- tvOS 앱 아이콘/Top Shelf 자산과 Release 빌드는 준비됐다. App Store Connect의 macOS·tvOS 통합 앱 레코드에 맞춰 공통 번들 ID `com.edwin.glaze`와 기존 관리형 배포 인증서를 사용한다.
- 2026-08-31 Apple TV 4K(3세대, tvOS 26.6)를 Xcode에 페어링·등록해 개발 프로파일을 만들고, 실기기에 설치한 빌드에서 Synology/Plex SSDP 발견과 Synology MKV 스트리밍 재생을 확인했다.
- tvOS 재생기는 Siri Remote 터치 탐색, 10초 이동, 내장·외부 자막 트랙 선택, 자막 싱크·크기 조정을 제공한다. UPnP 루트는 사진·음악 대신 실제 영상이 있는 컨테이너만 노출한다.
- Emby는 사무실 NAS, WebDAV 인증·한글 경로·sidecar 자막은 각 네트워크의 실기기 TestFlight에서 추가 검증한다.

Apple 플랫폼 네트워크 계약:

- macOS 15 이상 로컬 네트워크 접근 설명을 `NSLocalNetworkUsageDescription`으로 제공한다.
- iOS/iPadOS 실기기에서 SSDP 멀티캐스트를 사용할 때는 Apple의 multicast entitlement 승인 절차를 별도 진행한다.
- tvOS에서는 FFmpeg 실행 파일에 의존하지 않고, 네이티브 재생 트랙 또는 macOS에서 미리 준비한 SRT/VTT 자산을 소비한다.

## 글로벌 제공 전략

글레이즈는 한국 사용자에서 출발하되, 제품 자체는 글로벌 시장을 목표로 한다.

초기 기본 UI 언어:

- 한국어
- 영어

한국어는 초기 사용자의 기본 경험을 위해 중요하고, 영어는 글로벌 확장, App Store/웹사이트/문서/고객지원의 기준 언어가 된다.

이후 중요 국가별 확장 언어:

- 일본어
- 중국어 간체
- 중국어 번체
- 스페인어
- 프랑스어
- 독일어
- 포르투갈어
- 베트남어
- 인도네시아어
- 태국어

언어 확장은 한 번에 많이 추가하기보다, 실제 유입 국가와 결제 전환을 보고 우선순위를 조정한다.

## 번역 운영 방식

초기에는 번역기를 활용한 다국어 UI 번역을 사용할 수 있다. 다만 제품의 핵심 화면은 반드시 사람이 검수해야 한다.

권장 방식:

1. 한국어와 영어는 직접 작성한다.
2. 다른 언어는 기계 번역으로 초안을 만든다.
3. 결제, 개인정보, 오류, 권한, 다운로드, DRM 관련 문구는 사람이 검수한다.
4. 자주 쓰이는 UI 문구는 용어집으로 관리한다.
5. 앱 내 번역 품질 제보 기능을 둔다.

특히 자막/번역/DRM/다운로드 관련 문구는 오해가 생기면 정책 리스크가 커지므로 자동 번역만으로 배포하지 않는다.

## 제품 구조에 미리 반영할 것

플랫폼 확장은 나중이지만, 아래 구조는 지금 macOS 개발 단계부터 실제로 적용한다(더 이상 "고려 사항"이 아니라 아키텍처 전제다).

- `Package.swift`를 `GlazeCore`(플랫폼 독립 라이브러리 타겟)와 `GlazeMac`(macOS 전용 executable 타겟)으로 분리
- UI 문자열 분리와 localization 파일 관리
- 자막 생성 엔진과 UI의 분리 — `GlazeCore`에 위치
- 자막 포맷 처리 모듈의 플랫폼 독립화
- 작업 큐와 라이브러리 데이터 모델의 이식 가능성 — `GlazeCore`에 위치
- AI 자막 생성/번역 파이프라인(Core ML 기반)은 처음부터 `GlazeCore`에 두고 macOS/iOS 양쪽에서 공유
- VLC/libVLC 네이티브 재생 엔진은 macOS 전용이므로 `GlazeMac`에 격리(iOS는 AVFoundation/AVKit이 기본 경로가 될 가능성이 높음)
- 계정/동기화 도입 가능성을 고려한 데이터 구조
- `MediaAsset` 기반 파일/메타데이터/자막/시청 위치 분리
- 원본 파일 수정과 sidecar metadata 저장 정책 분리
- 플랫폼별 기능 플래그
- 다운로드/브라우저 확장 기능의 정책별 on/off 구조

## 내 의견

가장 좋은 순서는 다음과 같다.

1. macOS Apple Silicon에서 글레이즈의 핵심 가치를 완성한다.
2. 글로벌을 고려해 처음부터 한국어/영어 UI와 문서 구조로 만든다.
3. macOS에서 자막 생성/번역/라이브러리 준비 경험이 검증되면 iOS/iPadOS를 보조 감상 앱으로 확장한다.
4. 모바일에서 무리하게 긴 영상 생성까지 욕심내지 말고, 준비된 자막을 이어보는 경험부터 만든다.
5. 이후 글로벌 사용량과 수익성이 확인되면 Windows 데스크톱을 확장한다.
6. Android는 글로벌 모바일 수요가 명확해진 뒤, 엔진과 비용 구조가 안정됐을 때 진입한다.

즉, 글레이즈의 초기 정체성은 "macOS AI 자막 플레이어"이고, 장기 정체성은 "개인 영상 라이브러리를 모든 기기에서 자막화하고 감상하게 해주는 글로벌 AI 미디어 플랫폼"이다.
