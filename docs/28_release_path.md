# 출시까지 — 맥 · 아이폰 · 아이패드 · 애플TV

작성일: 2026-09-06

네 앱을 애플 개발자 센터를 거쳐 내보내기 위한 경로. **우리 손으로 끝낼 수 있는 것**과
**계정 소유자만 할 수 있는 것**, 그리고 **먼저 결정해야 답이 나오는 것**을 나눈다.

## 1. 끝난 것

| 항목 | 상태 |
|---|---|
| 아이폰·아이패드 앱 아이콘 | 없었다 → 만들었다 (`script/make_app_icons.py`) |
| 맥 아이콘의 회색 배경 | 둥근 사각형 바깥이 #F5F5F5로 칠해져 있었다 → 투명하게 |
| 프라이버시 매니페스트 | 없었다 → `Packaging/PrivacyInfo.xcprivacy`, 세 앱 모두 |
| 오픈소스 라이선스 고지 | 없었다 → 세 앱 모두 화면 추가, LGPL 전문 동봉 |
| VLC 런타임 서명 | 임시(ad-hoc) 서명이었다 → 릴리스는 앱과 같은 인증서로 |
| 수출 규정·저작권·카테고리 | plist에 없었다 → 채웠다 |
| TMDB 고지 문구 | TMDB 약관이 요구하는 문장이 빠져 있었다 → 넣었다 |
| 번들 구조 | VLC dylib 268개가 `Contents/Resources`에 있었다 → `Contents/Frameworks`로. 애플이 실행 코드를 두라고 정한 자리다 |
| 서명되지 않는 데이터 | `Frameworks` 아래 `.sofa` 데이터가 섞여 서명이 **실패**했다 → 데이터는 `Resources/vlc-share`로 |
| BD-J Java 아카이브 | `plugins/*.jar` 두 개가 들어 있었다. 쓰지 않는 블루레이용이고 앱스토어가 꺼리는 종류다 → 제거 |
| 쓰지 않는 40MB | VLC 자체 번역과 Lua 스크립트 → 제거. 런타임 105MB → 61MB |
| 플러그인 감사의 재현성 | 74개 GPL 플러그인 제거가 **손으로** 되어 있었다 → `Packaging/vlc-plugins.txt`가 고정하고 설치 스크립트가 강제한다 |
| 맥 릴리스 서명 | 개발용 인증서로 `--deep --strict` 검증 통과, 헬퍼 샌드박스 상속 확인, 옮긴 런타임에서 `libvlc_new` 성공 |

빌드는 세 타깃 모두 통과하고 테스트 224개가 통과한다.

## 2. 정해진 것 (2026-09-06)

- **앱 전체를 오픈소스로 공개한다.** 이것으로 LGPL §6은 해소된다 — 받은 사람이 소스를
  받아 고친 libVLC로 다시 링크할 수 있기 때문이다. 네 앱을 함께 낼 수 있다.
  소스 라이선스는 MIT(`LICENSE`), 재링크 방법은 `README.md`에 적었다
- **맥은 맥 앱스토어로 낸다.** 샌드박스는 이미 켜져 있다

아래 §3은 그 결정에 이르기까지 검토한 내용으로, 기록을 위해 남긴다.

## 3. 배경 — LGPL과 앱스토어

**이것이 가장 큰 갈림길이고, 기술이 아니라 판단의 문제다.**

재생 엔진 libVLC는 **LGPL-2.1**이다. LGPL은 "이 라이브러리를 쓴 프로그램"을 배포할 때,
사용자가 **라이브러리를 고쳐서 다시 링크할 수 있어야 한다**고 요구한다(§6).

| 플랫폼 | 링크 방식 | LGPL §6 대응 |
|---|---|---|
| **macOS** | 번들에 넣고 실행 중에 `dlopen` | 공유 라이브러리 방식이라 §6(b)에 해당한다. 사용자가 같은 이름의 라이브러리로 바꿔 넣을 수 있다. **비교적 안전** |
| **iOS · tvOS** | VLCKit이 실행 파일에 **정적 링크** | §6(a)를 택해야 한다 — 앱의 오브젝트 파일을 함께 제공해 사용자가 재링크할 수 있게 해야 한다 |

정적 링크 쪽이 문제다. 2011년 VLC가 앱스토어에서 내려간 것이 이 조항과 앱스토어 약관의
충돌 때문이었다. 지금 VLC가 앱스토어에 있는 것은 **VideoLAN이 저작권자여서** 스스로
예외를 둘 수 있기 때문이고, 제3자에게 그대로 적용되지 않는다.

**선택지**

1. **오브젝트 파일을 공개한다** — LGPL §6(a)를 문자 그대로 따른다. 앱의 `.o` 묶음과
   빌드 방법을 공개해 누구든 고친 VLCKit으로 다시 링크할 수 있게 한다. 소스 전체를
   공개할 필요는 없다. 실무적으로 가장 정직한 길이고, 실제로 이렇게 하는 앱이 있다
2. **앱 전체를 공개한다** — 가장 간단하고 논란이 없다
3. **iOS·tvOS의 재생 엔진을 바꾼다** — AVFoundation은 MKV를 열지 못하므로 사실상
   NAS의 영상 대부분을 포기하는 것이다. **권하지 않는다**
4. **맥만 먼저 낸다** — dlopen 방식이라 위험이 가장 낮다. 아이폰·애플TV는 1번이나 2번을
   정한 뒤에 낸다

**내 의견:** 4번으로 시작해 1번으로 간다. 맥은 지금 상태로 법적 위험이 낮고, 그 사이에
오브젝트 파일 공개 절차를 갖추면 된다. 다만 **이건 법률 자문이 아니다** — 배포 방식을
정하는 건 사용자의 몫이고, 필요하면 변호사에게 확인하는 게 맞다.

## 4. 계정을 직접 열어 확인한 것 (2026-09-07)

**앞선 추정은 대부분 틀렸다.** 계정 상태는 짐작보다 훨씬 앞서 있었다.

| 추정했던 것 | 실제 |
|---|---|
| 배포용 인증서가 없다 | 계정에 `Distribution Managed`와 `Mac Installer Distribution Managed`가 있다. **이 맥에 개인 키가 없을 뿐** |
| App ID를 플랫폼별로 등록해야 한다 | `com.edwin.glaze`가 이미 있고 iOS·iPadOS·macOS·tvOS·watchOS·visionOS를 전부 덮는다 |
| 앱 레코드를 셋 만들어야 한다 | 레코드 하나(Apple ID `6800189560`)에 macOS·tvOS가 있었다. **iOS만** 빠져 있었다 |
| 빌드를 한 번도 올린 적 없다 | macOS `1.0 (2)`가 2026-08-24에 올라가 있다 (이번 세션의 수정 이전 빌드라 교체 필요) |

### 이날 처리한 것

- **iOS 플랫폼 추가** → iOS·macOS·tvOS 세 버전이 모두 `1.0 Prepare for Submission`
- **앱 정보** — 부제 `맥에서 자막을 만들고, 어디서나 봅니다`, 카테고리 Entertainment / Photo & Video
- **App Privacy** — `Data Not Collected`. 애플의 정의("실시간 요청 처리에 필요한 시간을 넘겨
  기기 밖으로 전송", "앱에 코드를 넣은 서드파티")에 비추어 TMDB 조회는 해당하지 않는다
- **개인정보 처리방침** — URL과 Apple TV용 전문 입력
- **가격** 무료, **출시** 175개국 전체
- **세 플랫폼 모두** 설명·키워드·지원 URL·저작권 입력 (플랫폼마다 하는 일이 달라 문구도 다르다)

### 빌드 업로드 (2026-09-07)

| 플랫폼 | 빌드 | 상태 |
|---|---|---|
| macOS | `1.0 (6)` | 버전에 연결됨 |
| iOS | `1.0 (3)` | 버전에 연결됨 |
| tvOS | `1.0 (3)` | 버전에 연결됨 |

**빌드 번호가 저장소와 다르다.** `project.yml`은 `CURRENT_PROJECT_VERSION: 3`이지만
macOS는 (6)으로 올라갔다. Xcode의 `manageAppVersionAndBuildNumber`가 기본으로 켜져 있어,
이미 (5)까지 올라가 있던 것과 충돌하지 않도록 자동으로 올린 것이다. 다음에 올릴 때는
**macOS 기준 7 이상**이어야 한다.

`Apple Distribution` 인증서는 `-allowProvisioningUpdates`가 export 단계에서 만들었다.
그 인증서는 Xcode 자체 저장소에 있어 `security find-identity`에 **나오지 않는다** —
거기 없다고 서명이 실패한 것이 아니다. 패키지 안의 앱은
`Apple Distribution: TAESUNG YOO`로 서명되고 Mac Team Store 프로파일을 달고 있다.

수출 규정 항목은 `ITSAppUsesNonExemptEncryption`을 plist에 넣은 덕에 이미 해결되어 있다
(8월 빌드 하나는 `Missing Compliance`로 선택조차 되지 않는다).

`script/archive_and_upload.sh`가 이 과정을 그대로 반복한다.

### 남은 것 — 계정 소유자만 할 수 있다

1. **App Privacy의 `Publish`** — "응답이 정확하며 심사 지침과 관련 법을 준수함에 동의한다"는
   법적 확인이라 대신 누르지 않았다
2. **Content Rights** — 서드파티 콘텐츠 관련 선언
3. **연령 등급** — 임의의 영상을 재생하는 앱이라 설문의 답을 정해야 한다
4. **처리방침의 연락처 이메일** — `docs/PRIVACY.md`에 자리만 비워 두었다. 저장소가
   공개되어 있으므로 지금은 `—문의 이메일—`이 그대로 보인다
5. **스크린샷** — 세 플랫폼 모두 0장. 제출을 막는 마지막 실질 항목이다

## 5. 그다음 우리가 할 수 있는 것

- **스크린샷** — 아이폰 6.9"·아이패드 13"·애플TV 1920×1080·맥 2880×1800. 시뮬레이터에서
  뽑을 수 있다. 다만 보관함이 채워진 화면이라야 하므로 NAS 연결이 필요하다
- **앱 설명·키워드·개인정보 처리방침 URL** — 처리방침은 "아무것도 수집하지 않는다"는
  내용이면 되지만 **URL이 하나 필요하다** (App Store Connect 필수 항목)
- **연령 등급** — 사용자가 자기 파일을 재생하는 앱이라 4+로 볼 수 있으나, 임의의 영상을
  재생한다는 점에서 등급 설문의 답을 정해야 한다
- **아카이브와 업로드** — 인증서가 생기면 세 스킴 모두 archive → validate → upload
- **맥 배포 경로 결정** — 앱스토어(샌드박스, 이미 켜져 있음) / Developer ID + 공증
  (공증은 애플 ID 필요) / 둘 다

## 6. 저장소 공개 (2026-09-07)

공개 직전 점검에서 `docs/audits`의 앱 스크린샷에 **집과 회사 NAS의 실제 주소**가 찍혀 있는
것을 발견했다. 이미 원격 히스토리에 있어 파일 삭제로는 부족했고, `git-filter-repo`로 모든
커밋에서 이미지 35개를 들어낸 뒤 force-push했다. 새로 clone해 검증했다.

- 백업: `~/Projects/glaze-backup-20260907.bundle`
- 판단 근거인 README는 남기고, 이미지가 없는 이유를 문서에 적었다
- 텍스트 파일에는 주소가 없었고, TMDB 키·비밀번호·개인 이메일도 없었다
- 다른 도구가 남긴 `refs/codex/...` ref가 옛 객체를 붙잡고 있어 함께 정리했다

**교훈:** 앱 스크린샷은 그 자체가 개인정보다. 공개 저장소에 넣기 전에 사이드바와 설정
화면을 반드시 확인할 것.

## 7. 아직 확인되지 않은 채 남는 위험

출시 전에 닫는 게 좋다.

- **실기기 재생이 한 번도 확인되지 않았다.** 애플TV는 8월 31일부터 재생 때마다 죽고
  있었고(`docs/27`) 고쳤지만 실기기에서 확인하지 못했다. 아이폰도 시뮬레이터까지다
- **실기기 DLNA.** 시뮬레이터는 로컬 네트워크 권한을 강제하지 않는다. 실기기에서 권한이
  거부되면 조용히 실패하는데 그것을 알려주는 UI가 없다
- WebDAV 폴더 스캔 중 종료 (`docs/24`, 원인 미확인)
- 아이패드 탭바 중복 (`docs/25`)
