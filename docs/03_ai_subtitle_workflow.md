# AI 자막 생성 워크플로우

작성일: 2026-06-18  
프로젝트명: 글레이즈

## 핵심 방향

글레이즈의 AI 자막 기능은 재생 중 실시간 생성보다 "재생 전 사전 생성"을 중심으로 설계한다.

실시간 생성은 기술적으로 매력적이지만, 실제 감상 경험에서는 지연, 발열, 배터리 소모, 탐색 시 누락 문제가 생길 수 있다. 따라서 초기 핵심 경험은 백그라운드 사전 생성으로 잡는다.

## 기본 흐름

1. 사용자가 영상을 추가한다.
2. 앱이 sidecar와 영상 내장 자막 트랙을 함께 확인한다.
3. 사용자 선호 언어의 텍스트 내장 자막이 있으면 즉시 추출해 표시한다.
4. 선호 언어 자막이 없고 다른 언어의 텍스트 내장 자막이 있으면 해당 cue를 번역 입력으로 준비한다.
5. 재사용 가능한 텍스트 자막이 없을 때만 영상에서 오디오 트랙을 추출한다.
6. 오디오를 짧은 구간으로 나눈다.
7. 온디바이스 음성 인식 모델로 텍스트를 생성한다.
8. 문장 단위 타임스탬프를 정리한다.
9. 원어 자막 파일을 저장한다.
10. 필요하면 사용자 결과 언어의 번역 자막을 생성한다.
11. 생성된 자막을 영상과 자동 연결한다.
12. 재생 시 즉시 자막을 표시한다.

## 자막 입력 우선순위

1. 사용자 결과 언어와 일치하는 sidecar 또는 텍스트 내장 자막
2. 다른 언어의 텍스트 내장 자막 cue를 유지한 번역
3. 오디오 음성 인식 후 번역

PGS, VobSub 같은 이미지 기반 내장 자막은 트랙 존재를 표시하되 현재 번역 입력으로 사용하지 않는다. 후속 OCR 파이프라인이 검증되기 전에는 오디오 음성 인식으로 안전하게 fallback한다. 자막 검사와 추출만으로 AI 작업을 시작하지 않으며, 번역·음성 인식은 사용자의 명시적 요청 뒤에만 실행한다.

## 자막 상태

영상별 자막 상태는 명확하게 표시한다.

- 자막 없음
- 생성 대기 중
- 오디오 추출 중
- 음성 인식 중
- 자막 정리 중
- 번역 중
- 완료
- 실패
- 일시정지됨

## 백그라운드 처리 정책

기본 정책은 사용자의 Mac을 방해하지 않는 방향으로 둔다.

- 전원 연결 시 자동 생성
- 배터리 사용 중에는 기본적으로 일시정지
- 사용자가 재생하려는 영상은 우선순위 상승
- 긴 영상은 낮은 우선순위로 천천히 처리
- 사용자가 직접 "지금 생성"을 누르면 즉시 처리
- 발열이나 시스템 부하가 높으면 자동 속도 조절

## 자막 저장 정책

두 가지 저장 방식을 지원한다.

### 앱 내부 저장

기본값으로 사용한다. 원본 영상 폴더를 건드리지 않고 앱이 관리한다.

장점:

- 사용자가 파일 구조를 몰라도 됨
- 권한 문제 감소
- 캐시 관리가 쉬움

### 영상 옆 파일 저장

사용자가 선택하면 영상 파일 옆에 자막을 저장한다.

예:

- `movie.mkv`
- `movie.ja.srt` — 일본어 음성을 전사한 원문 자막
- `movie.ko.srt`

장점:

- 다른 플레이어에서도 사용 가능
- 사용자가 자막 파일을 직접 보관 가능

이 옵션은 최종 방향과 직결된다. **NAS 폴더를 마운트한 상태에서 "영상 옆"을 고르면, 자체 서버 패키지 없이도 자막이 NAS에 쌓이고 다른 기기가 그것을 가져다 쓴다.** 자세한 내용은 `21_media_server_vision.md`.

파일명은 Kodi·Jellyfin·Emby가 읽는 `영상명.<ISO 언어 코드>.srt`를 따른다. 음성 언어를 확정하지 못한 전사는 `movie.und.srt`로 저장한다. 과거 글레이즈가 만든 `movie.original.srt`, `movie.original.ko.srt`도 계속 감지하지만 새 파일에는 사용하지 않는다.

### 기본값을 뒤집는다 (2026-08-20 확정)

**"로컬 저장"과 "네트워크 저장"이라는 구분 자체가 틀렸다.** SMB로 마운트한 NAS는 `/Volumes` 아래의 평범한 파일 경로다. 사용자가 NAS에 있는 영상을 그대로 열어 번역하면, "영상 옆에 저장"이 곧 "NAS에 저장"이다. 실제 사용 방식이 이미 그렇다.

그래서 지금 동작은 NAS 사용자에게 **적극적으로 나쁘다.** 영상은 NAS에 있는데 자막만 Mac의 앱 컨테이너 안으로 떨어져 나가고, 다른 기기에서는 보이지 않는다.

기본값을 바꾼다.

1. **기본: 영상 옆에 저장한다.** 쓸 수 있는 경로가 있으면 그렇게 한다
2. **폴백: 앱 내부 저장.** 아래 경우에 자동으로 물러난다
   - DLNA 같은 네트워크 리소스라 쓸 수 있는 파일 경로가 없다
   - 읽기 전용 볼륨이다
   - 샌드박스가 그 폴더 쓰기를 허용하지 않는다
3. **사용자가 언제든 바꿀 수 있다.** 자막 패널의 "저장 위치" 행이 지금은 값이 고정된 라벨인데, 실제 선택 항목으로 만든다

**매번 묻지 않는다.** 번역할 때마다 대화상자를 띄우면 금방 성가셔진다. 한 번 정하고 기억하되, 결정이 어디에 있는지는 패널에서 항상 보이게 한다.

### 샌드박스 제약 — 여기가 실제 작업이다

코드를 확인한 결과, "영상 옆 저장"은 설정 항목 하나로 끝나지 않는다.

- **폴더를 열면 그 폴더 스코프가 생겨 안에 쓸 수 있다.** 현재 열기 패널이 폴더 선택을 허용하므로(`canChooseDirectories = true`) 이 경로는 이미 열려 있다
- **파일 하나만 열면 그 파일만 허가된다.** 형제 파일 쓰기는 보장되지 않는다. 저장 위치를 한 번 확인받거나 `NSIsRelatedItemType`으로 sidecar 관계를 선언해야 한다
- **보안 스코프 북마크를 저장하지 않는다.** 지금은 재생 시점에만 접근을 열고 닫는다. 앱을 다시 켜면 같은 NAS 폴더에 다시 쓰기 위해 재선택이 필요하다 — **북마크 영속화가 필요하다**

### iCloud는 "온라인 백업"이 아니다

기기 간 동기화를 넣을 때 문구에 주의한다. 우리 서버는 존재하지 않고, 저장되는 곳은 **사용자 자신의 iCloud**다. "온라인 백업"이라고 쓰면 우리가 어딘가로 올린다는 인상을 준다. "다른 기기에서도 보이게 iCloud에 함께 보관" 쪽이 사실에 맞다(`12_service_text_inventory.md`의 구현 용어 금지 원칙과 같은 맥락).

## 모델 모드

사용자는 성능과 정확도 사이에서 선택할 수 있어야 한다.

- 빠른 모드: 작은 모델, 빠른 처리, 정확도 보통
- 표준 모드: 중간 모델, 균형형
- 고정확도 모드: 큰 모델, 느리지만 더 정확함

기본값은 표준 모드로 둔다.

## 번역 자막

한국 사용자를 기준으로 한국어 번역은 핵심 기능이다.

지원 표시 방식:

- 원문 자막
- 한국어 자막
- 원문 + 한국어 이중 자막

초기에는 원어 자막 생성 후 번역하는 후처리 방식을 사용한다. 이후 필요하면 문장별 스트리밍 번역이나 요약 번역을 검토한다.

### 번역 단위 — 큐가 아니라 문장 (2026-08-20 확정)

자막 큐는 **표시 단위이지 언어 단위가 아니다.** 한 문장이 두세 큐에 걸쳐 잘려 있는 경우가 흔하고, 큐 하나만 번역 엔진에 넘기면 조각("Because he did.")이 들어가 시제·수·한국어 존댓말 레벨을 결정할 근거가 사라진다. 특히 한국어는 어순이 반대라 문장이 큐 경계에서 잘리면 문법 자체가 깨진다.

따라서 번역 파이프라인은 다음 순서를 따른다. 전부 `GlazeCore`에 있어 iOS/tvOS가 그대로 재사용한다.

1. `SubtitleSegmenter` — 연속 큐를 문장 단위로 묶는다. 종결 부호, 대사 하이픈, 가사 기호(♪)를 근거로 판단하며, 말줄임표는 **종결이 아니라 연결**로 본다(자막 관례). 구두점 없는 파일이 하나의 거대 세그먼트로 뭉치지 않도록 큐 5개·400자 상한을 둔다.
2. 엔진이 **문장 전체**를 번역한다.
3. `SubtitleRedistributor` — 번역문을 원래 큐 타이밍에 되돌린다. 원문에서 각 큐가 차지하던 비중대로 나누되, 목표 지점 근처의 문장부호 → 절 구분 → 어절 경계 순으로 붙여 단어 중간에서 잘리지 않게 한다.
4. `SubtitleTranslationAssembler` — 길이 비율 검증(원문 대비 0.15~6배)을 통과한 것만 반영하고, 실패한 세그먼트는 **원문을 유지**한다. 빈 자막으로 퇴화시키지 않는다.

큐 개수와 타이밍은 어떤 경우에도 보존된다. 이 성질은 테스트로 고정되어 있다.

### 모델 선택 — 측정을 위한 도입 (2026-08-20)

전사와 번역은 **성능과 품질에 각각 독립적으로 영향을 준다.** 전사가 이름을 잘못 알아들으면 번역 엔진이 아무리 좋아도 복구할 수 없다. 경쟁 제품(Submarine Player)도 전사 모델을 "고성능 ↔ 고정확도" 스펙트럼으로 노출하고, 번역은 온디바이스와 "Apple 제공 온라인 번역"을 구분한다.

엔진 결정을 감이 아니라 실측으로 하기 위해 두 축을 모두 선택 가능하게 했다.

**전사 모델** (`TranscriptionModelTier` → WhisperKit)

| 티어 | 모델 | 최초 다운로드 |
|---|---|---|
| 빠름 | `openai_whisper-base` | 140MB (실측) |
| 균형(기본) | `openai_whisper-small` | 465MB (실측) |
| 정확 | `openai_whisper-large-v3-v20240930_turbo` | 약 950MB (추정) |
| 최고 정확도 | `openai_whisper-large-v3` | 약 1.9GB (추정) |

**측정값 (2026-08-21, M시리즈, 12초 음성 클립)**

| | 소요 |
|---|---|
| 첫 실행 (모델 내려받기 포함) | 103.5초 |
| 이후 실행 (모델 캐시됨) | 7.4초 |

12초 오디오에 7.4초이므로 대략 **재생 시간의 0.6배**다. 두 시간짜리 영화면 `균형` 기준 한 시간 안팎이 걸린다는 뜻이고, 이 값이 백그라운드 처리 정책과 진행률 표시 설계의 근거가 된다.

turbo는 large-v3의 정확도를 유지하면서 디코더가 작아 Apple Silicon에서 초당 정확도가 가장 좋은 지점이다.

**번역 품질** (`SubtitleTranslationQuality` → `TranslationSession.Strategy`)

`빠름`(`.lowLatency`) / `고품질`(`.highFidelity`). 시스템 번역이 제공하는 **유일한 품질 레버**이며 macOS 26.4 이상에서만 존재한다(그 미만에서는 시스템이 자동 선택). **두 전략 모두 온디바이스로 확인했다(2026-08-21).** SDK 문서에는 설명이 없어 두 갈래로 검증했다.

1. 설치된 자산: `com.apple.sequoia.asset.mt.bi-en-zh-ja-ko.ko.20`(62MB)에 `MT/input_ko` · `handover_ko` · `decoder_ko`의 espresso 가중치가 들어 있다. 전략별로 다른 모델 자산은 존재하지 않는다 — 둘은 같은 모델을 다르게 돌리는 것이다.
2. 실제 계측: `.highFidelity`로 5개 큐를 영→한 번역하는 동안(약 5초) `nettop`으로 전 프로세스를 30초 샘플링했다. `translationd`와 `Glaze` 둘 다 소켓을 하나도 열지 않았다. 같은 샘플에 다른 프로세스들의 트래픽은 정상적으로 잡혔으므로 계측 누락이 아니다.

즉 시스템 번역은 네트워크 없이 동작하며, "온디바이스" 표기는 사실이다.

두 선택은 `UserDefaults`에 저장되고, 최근 전사/번역 소요 시간이 패널에 남는다. 측정값은 번역 섹션이 아니라 상위 섹션에 두는데, 번역이 성공하면 번역 섹션 자체가 사라지기 때문이다.

### 온디바이스 AI 엔진의 프롬프트 구조 (2026-08-21)

앱 없이 프롬프트를 실험할 수 있어야 반복 검증이 된다. `FoundationModels`는 명령줄에서도 그대로 쓸 수 있으므로, 같은 스키마·같은 지시문으로 6줄을 번역하는 작은 하니스를 만들어 비교했다. 아래 결론은 전부 그 하니스로 재현한 것이다(`sampling: .greedy`라 실행마다 결과가 같다).

**이웃 문장을 배경 문맥으로 넣지 않는다.** 프롬프트에 "Background — nearby dialogue"로 앞뒤 문장을 함께 넣으면, 모델이 **요청한 줄이 아니라 배경 줄을 번역해서** 돌려주는 일이 생긴다. 6줄 테스트에서 1번 자막이 3번 자막의 번역으로 나왔다. 문맥은 세션 대화 기록이 이미 들고 있으므로 프롬프트에는 번역할 줄만 넣는다.

**세션은 40개 세그먼트마다 새로 만든다.** 한 파일에 세션 하나가 이상적이지만 대화 기록이 줄마다 늘어난다. 장편 자막은 1,000줄이 넘어 중간에 컨텍스트 윈도를 넘긴다. 말투 규칙은 지시문에 있으므로 세션을 다시 만들어도 유지된다.

**필드 설명에 목표 언어를 반드시 적는다.** 이것이 이 엔진에서 만난 가장 심각한 버그였다. `@Guide(description: "The translated line only. …")`처럼 언어를 말하지 않으면, **여러 문장이 묶인 세그먼트에서 모델이 원문을 그대로 돌려준다.** 단문에서는 지시문만으로 알아듣기 때문에 드러나지 않다가, 실제 자막처럼 문장이 묶이는 순간 나타난다.

더 나쁜 것은 실패하는 방식이었다. 엔진은 응답을 받았으니 성공으로 세고, 어셈블러의 길이 비율 검사는 원문 복사를 통과시킨다(길이가 정확히 맞으니까). 결과적으로 **영어 원문이 담긴 파일이 `.ko.srt`라는 이름으로 저장되고 UI는 "번역 완료"라고 말한다.** 3회 재현했고 3회 모두 그랬다.

설명을 `"The translation only, written in the target language. Never a copy of the source. …"`로 바꾸면 사라진다.

안전장치도 함께 넣었다. `SubtitleTranslationAssembler.isEchoOfSource`가 공백·끝문장부호를 무시하고 원문과 비교해서, 원문 복사는 두 엔진 모두에서 **성공으로 세지 않는다**. 전부 복사로 돌아오면 이제 오류로 보고된다.

**스키마에 사고 단계를 하나 둔다.** `@Generable` 필드를 둘로 나눠 의미를 먼저 영어로 다시 쓰게 한 뒤 번역시킨다. 가이드 생성은 선언 순서대로 필드를 채우므로 앞 필드가 스크래치패드로 동작한다.

효과는 **문장 누락 방지**다. 단일 필드는 세 문장짜리 세그먼트에서 첫 문장을 통째로 잃었다("The letter arrived three weeks after the funeral"이 결과에 없음). 2필드는 세 문장이 모두 남는다.

| 방식 | 4개 세그먼트 소요 | 문장 누락 |
|---|---|---|
| 단일 필드 | 5.6초 | 발생 |
| 2필드(의미 → 번역) | 7.0초 | 없음 |

**이중부정은 여전히 신뢰할 수 없다.** 이전 판의 이 문서는 2필드 스키마가 이중부정을 해결했다고 적었는데, 그건 단문만으로 판단한 잘못된 결론이었다. 실제로는 같은 문장이 세그먼트 구성에 따라 맞기도 하고 틀리기도 한다 — 앱에서 `It wasn't that she didn't want to know…`는 "…의미하지 않았습니다"로 정확히 나왔지만, 하니스에서 다른 세그먼트와 함께 넣으면 "알고 싶어하지 않았지만"으로 뒤집혔다. 시스템 번역도 같은 문장을 틀린다. 온디바이스 모델 크기의 한계로 보고, 사용자 문서에 그대로 적는다.

### 번역 엔진 티어 (2026-08-20 확정)

| 티어 | 엔진 | 설치 | 시점 |
|---|---|---|---|
| 기본 | Apple Translation (시스템 번역) | 없음 | v1.0 |
| 고품질 | Apple Foundation Models (온디바이스 LLM) | 없음, Apple Intelligence 필요 | v1.0 |
| 확장 | 사용자가 직접 운영하는 OpenAI 호환 엔드포인트 | 사용자 | v3 (Pro 후보) |

Foundation Models를 v1.0에 넣는 이유는 확장이 아니라 **결함 보완**이기 때문이다. 시스템 번역으로는 한국어 말투를 지정할 수 없어 한 편 안에서 문체가 뒤섞인다(실측 확인). 플랫폼 확장 순서는 `06_platform_global_expansion_plan.md` 참고.

`SubtitleTranslationEngine` 프로토콜로 추상화되어 있어 엔진 추가는 교체이지 재작성이 아니다.

Apple Translation의 한계는 명확하다 — 문자열 in/out이라 **문맥과 한국어 말투를 지정할 방법이 없다.** 이 벽을 넘으려면 LLM 계열 엔진이 필요하고, 그래서 v1.0에 Foundation Models를 함께 넣는다(다운로드 0, 라이선스 리스크 0).

**로컬 LLM은 번들하지 않고 창구만 제공한다.** 사용자가 Ollama·LM Studio 등으로 직접 받은 모델을 가리키게 하며, 지켜야 할 경계는 다음 세 가지다.

- 앱이 모델 가중치를 대신 내려받지 않는다(내려받으면 사실상 배포자가 된다).
- 비상업 라이선스 모델을 유료 앱의 판매 포인트로 내세우지 않는다.
- 비상업 조항 모델을 상업적 워크플로우 대상으로 홍보하지 않는다.

국내 한국어 특화 모델(EXAONE 등)은 라이선스가 제각각이며 상당수가 비상업 조항을 둔다. 후보를 좁힌 뒤 **각 모델 라이선스 원문을 직접 확인하는 절차를 반드시 거친다** — `16_foundation_redesign_audit.md`의 VLC GPL 건과 동일한 유형의 리스크다. 또한 한국어 특화 모델은 **한국어 출력에만** 이득이므로, 글로벌 지향(`06_platform_global_expansion_plan.md`)과 맞추려면 범용 엔진을 기본으로 두고 출력 언어가 한국어일 때의 선택지로 붙이는 형태가 맞다.

## 실패 처리

실패는 조용히 숨기지 않고, 사용자가 이해할 수 있게 표시한다.

- 오디오 트랙 없음
- 지원하지 않는 코덱
- 모델 파일 없음
- 저장 권한 없음
- 처리 중 앱 종료
- 메모리 부족

실패한 작업은 재시도할 수 있어야 하며, 앱 재실행 후에도 대기열 상태가 유지되어야 한다.

## 개발 우선순위

1. 단일 영상 수동 자막 생성
2. 생성 자막 저장 및 자동 연결
3. 한국어 번역 자막 생성
4. 재생목록 내 자막 없는 영상 감지
5. 백그라운드 작업 큐
6. 전원/배터리 상태 기반 자동 처리
7. 작업 일시정지, 재개, 재시도
8. 영상 폴더 감시와 라이브러리 자동 준비
