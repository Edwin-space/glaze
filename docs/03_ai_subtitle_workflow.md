# AI 자막 생성 워크플로우

작성일: 2026-06-18  
프로젝트명: 글레이즈

## 핵심 방향

글레이즈의 AI 자막 기능은 재생 중 실시간 생성보다 "재생 전 사전 생성"을 중심으로 설계한다.

실시간 생성은 기술적으로 매력적이지만, 실제 감상 경험에서는 지연, 발열, 배터리 소모, 탐색 시 누락 문제가 생길 수 있다. 따라서 초기 핵심 경험은 백그라운드 사전 생성으로 잡는다.

## 기본 흐름

1. 사용자가 영상을 추가한다.
2. 앱이 sidecar와 영상 내장 자막 트랙을 함께 확인한다.
3. 사용자 선호 언어의 텍스트 내장 자막이 있으면 즉시 추출해 표시한다.
4. 선호 언어 자막이 없고 다른 언어의 텍스트 내장 자막이 있으면 해당 cue를 번역 입력으로 준비한다.
5. 재사용 가능한 텍스트 자막이 없을 때만 영상에서 오디오 트랙을 추출한다.
6. 오디오를 짧은 구간으로 나눈다.
7. 온디바이스 음성 인식 모델로 텍스트를 생성한다.
8. 문장 단위 타임스탬프를 정리한다.
9. 원어 자막 파일을 저장한다.
10. 필요하면 사용자 결과 언어의 번역 자막을 생성한다.
11. 생성된 자막을 영상과 자동 연결한다.
12. 재생 시 즉시 자막을 표시한다.

## 자막 입력 우선순위

1. 사용자 결과 언어와 일치하는 sidecar 또는 텍스트 내장 자막
2. 다른 언어의 텍스트 내장 자막 cue를 유지한 번역
3. 오디오 음성 인식 후 번역

PGS, VobSub 같은 이미지 기반 내장 자막은 트랙 존재를 표시하되 현재 번역 입력으로 사용하지 않는다. 후속 OCR 파이프라인이 검증되기 전에는 오디오 음성 인식으로 안전하게 fallback한다. 자막 검사와 추출만으로 AI 작업을 시작하지 않으며, 번역·음성 인식은 사용자의 명시적 요청 뒤에만 실행한다.

## 자막 상태

영상별 자막 상태는 명확하게 표시한다.

- 자막 없음
- 생성 대기 중
- 오디오 추출 중
- 음성 인식 중
- 자막 정리 중
- 번역 중
- 완료
- 실패
- 일시정지됨

## 백그라운드 처리 정책

기본 정책은 사용자의 Mac을 방해하지 않는 방향으로 둔다.

- 전원 연결 시 자동 생성
- 배터리 사용 중에는 기본적으로 일시정지
- 사용자가 재생하려는 영상은 우선순위 상승
- 긴 영상은 낮은 우선순위로 천천히 처리
- 사용자가 직접 "지금 생성"을 누르면 즉시 처리
- 발열이나 시스템 부하가 높으면 자동 속도 조절

## 자막 저장 정책

두 가지 저장 방식을 지원한다.

### 앱 내부 저장

기본값으로 사용한다. 원본 영상 폴더를 건드리지 않고 앱이 관리한다.

장점:

- 사용자가 파일 구조를 몰라도 됨
- 권한 문제 감소
- 캐시 관리가 쉬움

### 영상 옆 파일 저장

사용자가 선택하면 영상 파일 옆에 자막을 저장한다.

예:

- `movie.mkv`
- `movie.original.srt`
- `movie.ko.srt`

장점:

- 다른 플레이어에서도 사용 가능
- 사용자가 자막 파일을 직접 보관 가능

## 모델 모드

사용자는 성능과 정확도 사이에서 선택할 수 있어야 한다.

- 빠른 모드: 작은 모델, 빠른 처리, 정확도 보통
- 표준 모드: 중간 모델, 균형형
- 고정확도 모드: 큰 모델, 느리지만 더 정확함

기본값은 표준 모드로 둔다.

## 번역 자막

한국 사용자를 기준으로 한국어 번역은 핵심 기능이다.

지원 표시 방식:

- 원문 자막
- 한국어 자막
- 원문 + 한국어 이중 자막

초기에는 원어 자막 생성 후 번역하는 후처리 방식을 사용한다. 이후 필요하면 문장별 스트리밍 번역이나 요약 번역을 검토한다.

### 번역 단위 — 큐가 아니라 문장 (2026-08-20 확정)

자막 큐는 **표시 단위이지 언어 단위가 아니다.** 한 문장이 두세 큐에 걸쳐 잘려 있는 경우가 흔하고, 큐 하나만 번역 엔진에 넘기면 조각("Because he did.")이 들어가 시제·수·한국어 존댓말 레벨을 결정할 근거가 사라진다. 특히 한국어는 어순이 반대라 문장이 큐 경계에서 잘리면 문법 자체가 깨진다.

따라서 번역 파이프라인은 다음 순서를 따른다. 전부 `GlazeCore`에 있어 iOS/tvOS가 그대로 재사용한다.

1. `SubtitleSegmenter` — 연속 큐를 문장 단위로 묶는다. 종결 부호, 대사 하이픈, 가사 기호(♪)를 근거로 판단하며, 말줄임표는 **종결이 아니라 연결**로 본다(자막 관례). 구두점 없는 파일이 하나의 거대 세그먼트로 뭉치지 않도록 큐 5개·400자 상한을 둔다.
2. 엔진이 **문장 전체**를 번역한다.
3. `SubtitleRedistributor` — 번역문을 원래 큐 타이밍에 되돌린다. 원문에서 각 큐가 차지하던 비중대로 나누되, 목표 지점 근처의 문장부호 → 절 구분 → 어절 경계 순으로 붙여 단어 중간에서 잘리지 않게 한다.
4. `SubtitleTranslationAssembler` — 길이 비율 검증(원문 대비 0.15~6배)을 통과한 것만 반영하고, 실패한 세그먼트는 **원문을 유지**한다. 빈 자막으로 퇴화시키지 않는다.

큐 개수와 타이밍은 어떤 경우에도 보존된다. 이 성질은 테스트로 고정되어 있다.

### 모델 선택 — 측정을 위한 도입 (2026-08-20)

전사와 번역은 **성능과 품질에 각각 독립적으로 영향을 준다.** 전사가 이름을 잘못 알아들으면 번역 엔진이 아무리 좋아도 복구할 수 없다. 경쟁 제품(Submarine Player)도 전사 모델을 "고성능 ↔ 고정확도" 스펙트럼으로 노출하고, 번역은 온디바이스와 "Apple 제공 온라인 번역"을 구분한다.

엔진 결정을 감이 아니라 실측으로 하기 위해 두 축을 모두 선택 가능하게 했다.

**전사 모델** (`TranscriptionModelTier` → WhisperKit)

| 티어 | 모델 | 최초 다운로드 |
|---|---|---|
| 빠름 | `openai_whisper-base` | 약 150MB |
| 균형(기본) | `openai_whisper-small` | 약 250MB |
| 정확 | `openai_whisper-large-v3-v20240930_turbo` | 약 640MB |
| 최고 정확도 | `openai_whisper-large-v3` | 약 1.6GB |

turbo는 large-v3의 정확도를 유지하면서 디코더가 작아 Apple Silicon에서 초당 정확도가 가장 좋은 지점이다.

**번역 품질** (`SubtitleTranslationQuality` → `TranslationSession.Strategy`)

`빠름`(`.lowLatency`) / `고품질`(`.highFidelity`). 시스템 번역이 제공하는 **유일한 품질 레버**이며 macOS 26.4 이상에서만 존재한다(그 미만에서는 시스템이 자동 선택). Apple이 `.highFidelity`를 어떻게 처리하는지(더 큰 온디바이스 모델인지 서버 경유인지)는 공개 문서로 확인하지 못했다 — 온디바이스 포지셔닝과 관련되므로 **출시 전 실제 동작 확인이 필요하다.**

두 선택은 `UserDefaults`에 저장되고, 최근 전사/번역 소요 시간이 패널에 남는다. 측정값은 번역 섹션이 아니라 상위 섹션에 두는데, 번역이 성공하면 번역 섹션 자체가 사라지기 때문이다.

### 번역 엔진 티어 (2026-08-20 확정)

| 티어 | 엔진 | 설치 | 시점 |
|---|---|---|---|
| 기본 | Apple Translation (시스템 번역) | 없음 | v1.0 |
| 고품질 | Apple Foundation Models (온디바이스 LLM) | 없음, Apple Intelligence 필요 | v1.0 |
| 확장 | 사용자가 직접 운영하는 OpenAI 호환 엔드포인트 | 사용자 | v3 (Pro 후보) |

Foundation Models를 v1.0에 넣는 이유는 확장이 아니라 **결함 보완**이기 때문이다. 시스템 번역으로는 한국어 말투를 지정할 수 없어 한 편 안에서 문체가 뒤섞인다(실측 확인). 플랫폼 확장 순서는 `06_platform_global_expansion_plan.md` 참고.

`SubtitleTranslationEngine` 프로토콜로 추상화되어 있어 엔진 추가는 교체이지 재작성이 아니다.

Apple Translation의 한계는 명확하다 — 문자열 in/out이라 **문맥과 한국어 말투를 지정할 방법이 없다.** 이 벽을 넘으려면 LLM 계열 엔진이 필요하고, 그래서 v1.0에 Foundation Models를 함께 넣는다(다운로드 0, 라이선스 리스크 0).

**로컬 LLM은 번들하지 않고 창구만 제공한다.** 사용자가 Ollama·LM Studio 등으로 직접 받은 모델을 가리키게 하며, 지켜야 할 경계는 다음 세 가지다.

- 앱이 모델 가중치를 대신 내려받지 않는다(내려받으면 사실상 배포자가 된다).
- 비상업 라이선스 모델을 유료 앱의 판매 포인트로 내세우지 않는다.
- 비상업 조항 모델을 상업적 워크플로우 대상으로 홍보하지 않는다.

국내 한국어 특화 모델(EXAONE 등)은 라이선스가 제각각이며 상당수가 비상업 조항을 둔다. 후보를 좁힌 뒤 **각 모델 라이선스 원문을 직접 확인하는 절차를 반드시 거친다** — `16_foundation_redesign_audit.md`의 VLC GPL 건과 동일한 유형의 리스크다. 또한 한국어 특화 모델은 **한국어 출력에만** 이득이므로, 글로벌 지향(`06_platform_global_expansion_plan.md`)과 맞추려면 범용 엔진을 기본으로 두고 출력 언어가 한국어일 때의 선택지로 붙이는 형태가 맞다.

## 실패 처리

실패는 조용히 숨기지 않고, 사용자가 이해할 수 있게 표시한다.

- 오디오 트랙 없음
- 지원하지 않는 코덱
- 모델 파일 없음
- 저장 권한 없음
- 처리 중 앱 종료
- 메모리 부족

실패한 작업은 재시도할 수 있어야 하며, 앱 재실행 후에도 대기열 상태가 유지되어야 한다.

## 개발 우선순위

1. 단일 영상 수동 자막 생성
2. 생성 자막 저장 및 자동 연결
3. 한국어 번역 자막 생성
4. 재생목록 내 자막 없는 영상 감지
5. 백그라운드 작업 큐
6. 전원/배터리 상태 기반 자동 처리
7. 작업 일시정지, 재개, 재시도
8. 영상 폴더 감시와 라이브러리 자동 준비
