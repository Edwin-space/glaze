# 네트워크 스트리밍 — 실기기에서 왜 안 되는가 (2026-09-08)

실기기에서 **시놀로지 연결 실패**, **DLNA/UPnP 검색 결과 없음**, 사실상 네트워크 관련
전부가 동작하지 않는다는 보고. 원인은 **하나가 아니라 셋**이고, 서로 독립적이다.
셋 다 **시뮬레이터에서는 드러나지 않는다** — 그래서 지금까지 통과했다.

## 1. 시놀로지 — 스스로 서명한 인증서 (고침)

`SynologyAddress`는 주소만 적으면 `https://호스트:5001`로 만든다. DSM이 기본으로 그
포트에 세워두는 인증서는 **시놀로지가 스스로 서명한 것**이다. 아무도 보증하지 않으므로
`URLSession`이 연결을 끊는다 — 옳은 동작이다.

문제는 그다음이었다. `SynologyClient`와 `WebDAVClient`는 `URLSession.shared`를
델리게이트 없이 쓰고 있었다. 서버 신뢰 문제를 **처리할 자리가 아예 없었다.**
그래서 집에 있는 NAS는 주소와 계정이 다 맞아도 연결되지 않고, 화면에는
"NAS에 연결하지 못했습니다"만 떴다. 사람을 있지도 않은 네트워크 장애를 찾게 만든다.

**검사를 끄는 것은 답이 아니다.** 사람이 인증서를 한 번 보고 "그래, 내 NAS다"라고
말하면, **그 인증서 하나를 그 호스트에 고정한다**. 나중에 다른 인증서가 오면 다시
묻는다 — 그게 고정의 요점이다.

- `ServerTrustStore` — 받아들인 지문(SHA-256)을 호스트별로 보관
- `ServerTrustDelegate` — 시스템이 통과시키면 그대로 두고, 아니면 지문을 계산해
  고정된 것과 대조. 맞지 않으면 **거절하고 무엇을 봤는지 기록**한다
- 실패한 화면이 그 기록을 꺼내 지문과 함께 보여주고, "신뢰하고 연결"을 누르면 고정 후
  재시도

**셀프 서명 서버를 실제로 세워 검증했다** — TLS 핸드셰이크가 거절되고, 지문이 잡히고,
받아들인 뒤에는 연결되고, 지문이 다르면 다시 거절된다(`ServerTrustHandshakeTests`).

## 2. DLNA/UPnP — 멀티캐스트 권한이 없다 (우리 손으로 못 고침)

SSDP 검색은 `239.255.255.250:1900`으로 보낸다. **멀티캐스트다.**

iOS 14부터 멀티캐스트를 보내려면 `com.apple.developer.networking.multicast`
엔타이틀먼트가 필요하고, 이것은 **애플에 신청해서 승인받아야** 얻는다. 지금 iOS 타깃에는
**엔타이틀먼트 파일 자체가 없다.**

시뮬레이터는 이 제한을 강제하지 않는다. 그래서 시뮬레이터에서는 잘 되고 실기기에서는
아무것도 찾지 못한다 — 보고된 증상 그대로다.

**코드로 고칠 수 없다.** 필요한 것:

1. 애플에 멀티캐스트 엔타이틀먼트 신청 (developer.apple.com의 요청 양식,
   계정 소유자만 가능)
2. 승인되면 App ID에 능력을 켜고, `Packaging/GlazeiOS.entitlements`를 만들어
   프로젝트에 붙인다

**승인 전에 엔타이틀먼트를 먼저 넣으면 안 된다** — 프로비저닝 프로파일에 없는 능력을
요구하면 코드 서명이 실패해서 빌드가 통째로 깨진다. 그래서 지금은 넣지 않았다.

그때까지 아이폰·아이패드에서 **DLNA 자동 검색은 동작하지 않는다.** 수동으로 주소를
넣는 시놀로지·WebDAV 경로는 멀티캐스트와 무관하므로 영향받지 않는다.

## 3. 로컬 네트워크 권한 — 거부되면 전부 조용히 죽는다 (알리도록 고침)

같은 네트워크의 기기에 접속하려면 iOS가 **로컬 네트워크 권한**을 묻는다. 한 번
"허용 안 함"을 누르면 그 뒤로는 묻지 않고, 사설 주소로 가는 모든 연결이 실패한다.
시놀로지도 WebDAV도 DLNA도 한꺼번에 죽는다 — "네트워크 관련 전부가 안 된다"는 보고와
정확히 맞는다.

**앱이 이 권한 상태를 물어볼 수 있는 API가 iOS에 없다.** 그래서 감지하는 척하지 않고,
연결이 실패했을 때 확인할 자리를 알려준다 — 시놀로지 설정 화면과 미디어 소스 화면
양쪽에.

> 연결되지 않으면 설정 › 글레이즈 › 로컬 네트워크가 켜져 있는지 확인하세요.

시뮬레이터는 이 권한을 강제하지 않는다. 이것도 실기기에서만 드러난다.

## 확인 순서 (실기기)

1. **설정 › 글레이즈 › 로컬 네트워크**가 켜져 있는가 — 꺼져 있으면 여기서 끝이다
2. 시놀로지 주소를 넣고 연결 → 인증서 시트가 뜨면 **지문을 NAS의 것과 대조**한 뒤
   신뢰. 이제 연결되어야 한다
3. DLNA 자동 검색은 멀티캐스트 승인 전까지 빈 목록이다. 정상이다

## 아직 확인하지 않은 것

- **실기기에서의 시놀로지 연결 성공.** 인증서 경로는 셀프 서명 서버로 검증했지만,
  실제 NAS에 붙여보지 않았다
- **스트리밍 재생 자체.** 연결이 막혀 있어 그 너머를 아직 보지 못했다.
  연결이 뚫린 뒤에 확인해야 한다
- **WebDAV의 인증서 시트.** 오류 문구와 경로는 넣었지만 시놀로지 쪽만 시트를 붙였다
- 원격(공개 주소) NAS의 ATS. `NSAllowsLocalNetworking`은 사설 주소만 열어준다 —
  공개 IP에 평문 HTTP로 붙는 것은 여전히 막힌다(그리고 막는 게 맞다)

## 4. TLS 오류의 진짜 원인 — 인증서가 아니라 주소였다 (2026-09-08, 고침)

실기기에서 다시 올라온 오류:

```
NAS에 연결하지 못했습니다 — TLS 오류로 인해 보안 연결이 실패했습니다.
· (-1200) · tls -9802 · kCFErrorDomainCFNetwork -1200
```

주소는 `203.0.113.10`, 포트 기본값 5001. 맥에서 직접 그 서버에 붙어봤다:

```
$ openssl s_client -connect 203.0.113.10:5001
 0 s:/CN=my-nas.synology.me
   i:/C=US/O=Let's Encrypt/CN=YE2
Verify return code: 0 (ok)

$ curl -v https://203.0.113.10:5001/
* subjectAltName does not match ipv4 address 203.0.113.10
* SSL: no alternative certificate subject name matches target ipv4 address

$ curl https://my-nas.synology.me:5001/webapi/query.cgi?...
http=200 tls=0
{"data":{"SYNO.API.Auth":{...}},"success":true}
```

**이 NAS는 스스로 서명한 인증서를 쓰지 않는다.** DSM이 받아둔 정식 Let's Encrypt
인증서가 `my-nas.synology.me` 앞으로 발급되어 있다. 그런데 사람이 그 이름이 아니라
그 이름이 가리키는 **IP를 적었다.** 인증서에는 IP가 적혀 있지 않으므로 이름 검사가
실패하고, 핸드셰이크가 끊긴다.

`docs/34`의 1번(자체 서명 인증서 고정)은 옳은 기능이지만 **이 서버의 문제가 아니었다.**
그래서 "신뢰하고 연결"이 답으로 보이지 않았던 것이다.

### 고친 것

여기서 지문을 보여주고 "신뢰하고 연결"을 권하는 것은 **틀린 조언**이다. 서버는
멀쩡하고, 경고는 사실을 말하고 있다. 사람에게 옳은 경고를 무시하는 법을 가르치는 대신,
**한 번 눌러 제대로 고치게** 한다.

- `ServerCertificate.certifiedName` — 인증서에 적힌 이름. 그 이름으로 **다시 검증해서
  통과할 때만** 채워진다. 자체 서명 인증서라면 이름을 바꿔도 똑같이 실패하므로 비어 있고,
  그때는 지금까지처럼 지문을 보여준다
- 시트가 두 갈래가 된다: 이름 문제면 *"주소를 바꿔야 합니다 — 이 서버의 인증서는
  my-nas.synology.me 앞으로 정식 발급되어 있습니다"* 와 **`my-nas.synology.me로 연결`**
  버튼. 그 외에는 기존의 지문 확인
- 와일드카드(`*.my-nas.synology.me`)는 주소창에 넣을 수 없으므로 아래의 맨 이름을 쓴다

`doesNotSuggestANameThatWouldAlsoFail` — 자체 서명 서버의 CN이 달라도 이름 변경을
권하지 않는다는 회귀 테스트. 306개 통과.

### 사용자가 할 것

주소를 **`my-nas.synology.me`** 로 바꾼다. IP가 아니라. 그러면 인증서가 정상 검증되어
신뢰 시트 자체가 뜨지 않는다.

## 부록 (2026-09-19) — 애플TV도 같은 제한을 받는다

위 2절은 iOS만 적었지만, **tvOS에도 같은 멀티캐스트 제한이 적용된다.** 애플TV 실기기에서
DLNA 서버가 하나도 보이지 않고, WebDAV를 함께 설정했을 때만 데이터가 보이던 증상의 원인이
이것이다 — WebDAV는 주소를 직접 입력하므로 멀티캐스트와 무관하게 동작한다.

승인을 기다리는 동안의 대응은 `docs/47`에 적었다: 주소를 입력해 서버 하나에게 직접 묻는
길(유니캐스트 SSDP + 알려진 설명 파일 주소)을 만들었다.
